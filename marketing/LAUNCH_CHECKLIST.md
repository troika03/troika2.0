# План маркетингового запуска и критерии допуска

Редакция 2026-10-16. Подставить ответственного и фактические даты при исполнении. Метка [ ] означает **не выполнено по этому плану**, а не утверждение об отсутствии кода.

## Фаза A — 0–7 дней: подготовка к закрытой бете
- [ ] Владелец: выбрать **постоянный домен**, зафиксировать HTTPS и правильные 301/robots/sitemap/canonical/OG до SEO-продвижения.
- [ ] QA: проверить живую связку Android/Windows `register → login → voice → agent → результат → повторный вход` на актуальных установщиках; сохранить результаты с версиями.
- [ ] QA: проверить скачивание/подписи/хеши актуального APK и ZIP; не путать сборку 12 октября с source 16 октября.
- [ ] Product: записать 3 реальных видео (поиск, документ, код) без вымышленных экранов/данных.
- [ ] Legal/security: проверить контакты оператора, privacy/terms/cookies, несовершеннолетних пользователей/разрешённый возраст, надёжность хранилищ, удаление/экспорт, уведомление об обработчиках.
- [ ] Support: определить время ответа, три категории проблем и способ собирать обратную связь добровольно.
- [ ] Owner: выбрать 20–50 участников ограниченной беты, способ одобрения и отзыва доступа; не публиковать несуществующую автоматическую очередь.

## Фаза B — 8–21 день: проверка спроса
- [ ] Опубликовать посты 1–9 из `CONTENT_PLAN.md` только в собственных каналах / с разрешения сообществ.
- [ ] Вручную по согласию пригласить небольшую beta-кохорту; не отправлять массовый спам.
- [ ] Для каждого сценария сверять обещание на лендинге с исходным билдом.
- [ ] Собирать в агрегате: сколько людей начали, у скольких получился 1 полезный результат, сколько вернулось, основные блокеры.
- [ ] Два раза в неделю разбирать обратную связь с разработкой; фиксировать исправленный баг и повторный тест.
- [ ] Если сценарий не работает — остановить конкретный ролик и исправить либо убрать обещание.

## Фаза C — 22–30 день: оценка
- [ ] Обновить FAQ/скриншоты и тексты по замечаниям реальных пользователей.
- [ ] Проверить безопасность, стабильность, стоимость токенов/STT, обращений и количество ручных операций.
- [ ] Решить на основании фактов: продолжать бету, расширить её или готовить платный релиз.
- [ ] Зафиксировать базовые показатели без придуманных «бенчмарков»: регистрация→первый результат, качество сценария, повтор через 7 дней.
- [ ] Написать короткий итог месяца для сообщества (подтверждённые улучшения, ограничения, следующий шаг).

## Не запускать платную продажу, пока не закрыты все gates
| Владелец | Gate | Доказательство |
|---|---|---|
| QA | Сквозной E2E сайта и актуальных Android/Windows клиентов | Логи/скринкаст с билдом, без личных данных |
| Backend | production backup/restore, изоляция аккаунтов, мониторинг ошибок | Проверка восстановления и удаления |
| Billing | merchant, checkout, renew/cancel/refund, webhooks, лимиты расходов | Финансовые и технические E2E |
| Legal | оператор, условия, privacy, поддержка, допустимая возрастная группа | Опубликованные проверенные документы |
| Product | стабильные сценарии для рекламы, реальные демо | QA sign-off и записанный результат |
| Marketing | постоянный домен и SEO, корректные обещания, privacy-safe учёт | Проверка HTML/robots/sitemap и согласованный план |

Общий источник решений: `docs/TROIKA_1_0_EXECUTION_TRACKER.md`; данный файл не заменяет разделы 18–20 и главный DOCX.

## После выпуска (не сейчас)
Запускать платное привлечение маленькими тестами; ограничивать расходы, сравнивать активированные когорты, не менять цену/модель в рекламе без решения владельца. Если скачивание ломается или CAC выше валовой маржи — приостановить кампанию, а не докупать показы.
