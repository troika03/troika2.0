# Синхронизация данных аккаунта Troika

## Решение продукта

Аккаунт является владельцем пользовательских данных. Телефон и Windows-клиент,
вошедшие в один аккаунт, показывают одну историю, память, задачи, напоминания,
общие настройки. Сервер хранит основную копию этих данных. Клиенты хранят локальный
кэш для быстрого запуска и ограниченной офлайн-работы.

Это решение заменяет прежнее требование, по которому устройство было
единственным каноническим хранилищем. Для Troika 1.0 важнее автоматическое
восстановление данных после входа в аккаунт. Строгое E2EE с невосстановимым
пользовательским ключом не является требованием версии 1.0.

Решение владельца от 6 октября 2026 года делает исключение для готовых новых
документов, презентаций и проектов с кодом: основная файловая копия хранится
на устройстве. ИИ и история остаются облачными; содержимое запроса и ответа
может присутствовать в истории, но бинарный файл не записывается в ArtifactStore.
Сервер собирает его в RAM и передаёт только устройству-создателю; подтверждение
получения удаляет RAM-копию, иначе TTL — 10 минут. Обрыв/restart/TTL требуют
повторной генерации, если локального файла ещё нет. Старые облачные файлы
доступны как раньше. Автоматического backup/синхронизации новых локальных файлов
между устройствами нет; после удаления приложения локальный файл может быть потерян.

## Статус реализации на 2026-10-05

Реализованы owner-scoped серверные stores, общий `home_session_id`,
загрузка истории после входа и polling открытого клиента. Полная
offline-first SQLite/очередь, change feed, tombstones и conflict resolution
ниже являются целевой архитектурой, а не существующей гарантией.
Recovery, подтверждение почты и production backup lifecycle ещё отсутствуют.

## Пользовательский сценарий

1. Пользователь создаёт аккаунт или входит в существующий.
2. Сервер возвращает стабильный идентификатор основной беседы аккаунта.
3. Клиент загружает историю, память, задачи, напоминания; показывает локальные
   файлы и доступные прежние облачные artifacts.
4. Изменения отправляются с токеном конкретного устройства, но принадлежат
   аккаунту.
5. Другой клиент того же аккаунта получает изменения при открытии раздела или
   во время периодического обновления.
6. Отзыв устройства немедленно закрывает его токены и активные соединения, но
   не удаляет данные аккаунта.
7. Удаление аккаунта удаляет данные во всех основных хранилищах согласно
   политике удаления и резервного копирования.

## Модель данных

- Основная беседа имеет один `home_session_id` на аккаунт.
- Дополнительные беседы также принадлежат аккаунту. `device_id` хранит
  устройство-создатель и не ограничивает доступ другого устройства владельца.
- Память, проекты, задачи, заметки, inbox и notification preferences имеют
  обязательный `user_id`.
- Прежние облачные файлы имеют owner-scoped metadata и bytes. Новые готовые
  файлы updated client хранит локально; временная передача привязана к owner/device.
  При редактировании создаётся новая версия; оригинал не перезаписывается.
- Удаление синхронизируемого объекта в будущей офлайн-очереди представляется
  tombstone-записью, чтобы другой клиент не восстановил удалённый объект.

## Разрешение конфликтов

- Сообщения добавляются и не перезаписываются.
- Файлы получают отдельные версии.
- Для простых настроек используется последняя подтверждённая сервером версия.
- Для задач применяется версия записи; сервер отклоняет изменение устаревшей
  версии и клиент предлагает повторить действие.
- Для одновременно изменённого пользовательского текста сохраняются обе
  версии до выбора пользователя.

## Безопасность

- Сервер определяет `user_id` и `device_id` только по access token. Клиент не
  может выбрать владельца в теле запроса.
- Каждый запрос повторно проверяет активность пользователя, устройства и
  токена.
- Передача идёт только через HTTPS/WSS.
- Production БД, объектное хранилище и резервные копии должны использовать
  шифрование at rest и отдельные ключи окружения.
- Секреты, пароли, bearer tokens, prompts и содержимое файлов не попадают в
  application logs или аналитику.
- Смена пароля и подтверждённая почта обеспечивают автоматическое
  восстановление доступа к данным. Recovery flow реализуется до продаж.

## Этапы реализации

### Этап 1 — общая онлайн-копия

- Один `home_session_id` на аккаунт.
- Продолжение основной беседы с любого активного устройства аккаунта.
- Автоматическая загрузка истории после входа.
- Периодическое обновление открытого клиента.
- Существующие owner-scoped API памяти, задач, напоминаний и файлов остаются
  общей серверной копией аккаунта.

### Этап 2 — надёжный offline-first кэш

- Локальная SQLite на каждом клиенте.
- Очередь исходящих изменений с idempotency key.
- Серверный монотонный cursor/change feed.
- Tombstones, версии записей и контролируемое разрешение конфликтов.
- Повторная отправка после восстановления сети без дублей.

### Этап 3 — production storage

- PostgreSQL для metadata и change feed.
- Private object storage для старых серверных artifacts и их версий; новые
  локальные документы не загружаются туда автоматически.
- Очередь фоновых операций.
- Зашифрованные резервные копии, restore rehearsal и проверенное удаление.
- Наблюдаемость без содержимого пользовательских данных.

## Definition of Done

- Сообщение, память или задача, созданные на телефоне, доступны в Windows
  после входа в тот же аккаунт, и наоборот.
- Старые серверные artifacts доступны устройствам аккаунта. Новые документы
  и проекты с кодом остаются на создавшем устройстве; перенос и резервирование
  этих локальных файлов не входят в текущую автоматическую синхронизацию.
- Другое устройство владельца может продолжить основную беседу.
- Другой аккаунт не может прочитать объект по ID или продолжить его сессию.
- Повтор запроса не создаёт дубликат.
- Отзыв устройства прекращает его доступ без потери данных аккаунта.
- Удаление аккаунта удаляет основную серверную копию, серверные файлы и доступные резервные копии по
  утверждённой политике.
