# TROIKA PC — план: Тройка как приложение для ПК (Windows)

> **Режим: LOCAL-FIRST (без удалённого сервера).** Пока всё крутится на самой машине:
> gateway (мозг + tools) запускается локально на `127.0.0.1:8642`, приложение и PC-tools —
> на том же ПК. Удалённый VPS не участвует. Вопрос «сервер/облако» откладываем — решим
> потом. Ключевое следствие: **мост клиент↔сервер (`pc_bridge`) НЕ нужен** — раз gateway
> на той же машине, PC-tools работают прямо в процессе, обычными локальными tools.

**Цель.** Полноценная Тройка на ПК в виде **Flutter-приложения под Windows**, которое:
1. умеет **всё, что умеют Тройка и Hermes** (память, кодеры, web_research, telegram,
   генерация медиа, автопилот, проекты и т.д.) — наследуется бесплатно: тот же локальный
   gateway, что и на сервере, просто на `localhost`;
2. **сверху** добавляет управление самим ПК и работу с локальными программами/файлами;
3. по типу задачи сама выбирает путь: **надёжная генерация файла** или **живое управление
   на экране** (гибрид, приоритет — надёжность).

## 1. Архитектура (local-first, всё на одной машине)

```
┌───────────────────────────────────────────────────────────┐
│  ПК пользователя (всё локально)                           │
│                                                           │
│  Flutter Windows app ──HTTP/SSE──► gateway 127.0.0.1:8642 │
│  ├ голос (STT/TTS/wake)            ├ мозг (LLM)            │
│  └ лента чата (как Android)        ├ память SOMA/GROUND    │
│                                    ├ ВСЕ существующие tools│
│                                    ├ pc_tool.py  (НОВОЕ,   │
│                                    │   in-process, без моста)│
│                                    └ pptx/docx/xlsx (есть) │
└───────────────────────────────────────────────────────────┘
```

**Принцип.** Мозг и все tools — в локальном gateway на `localhost`. PC-tools трогают
реальную машину напрямую из процесса gateway (тот же ПК) — никакого WebSocket-моста и
никакого удалённого исполнителя не требуется. Это заметно проще, чем phone-схема
(`android_tool` → `phone_bridge` → телефон), потому что там клиент и мозг на разных
устройствах, а здесь — на одном.

**Наследование возможностей.** Ничего не портируем: тот же Hermes-gateway, что крутится
на VPS, запускаем на ПК (`python cli.py --gateway`, порт 8642 — память
`troika-gateway-entry`). Все существующие tools работают. PC-версия добавляет только новое.

> Когда позже вернёмся к «серверу/облаку»: если понадобится рулить ПК с телефона или из
> облака, тогда добавим `pc_bridge.py` + удалённый executor по образцу phone_bridge. Сейчас
> это НЕ делаем.

## 2. Развилка «файл vs живое управление» (гибрид)

Выбор делает сам мозг через существующий `find_tool`-роутер по формулировке задачи.

**Путь А — генерация файла (по умолчанию, надёжный).** Задача = «на выходе документ»:
презентация, Word, Excel, письмо, отчёт, картинка/видео.
→ мозг собирает контент → серверный tool генерирует файл → файл доставляется на ПК →
`pc_open_file` открывает его на экране. Быстро, без промахов мышкой.

**Путь Б — живое управление (когда файла на выходе нет).** «Открой Spotify», «сверни
всё», «зайди на сайт и нажми туда», «настрой программу».
→ `pc_gui_control` в Local Executor: клик/ввод/скриншот через Windows UIAutomation +
pyautogui. Видно, как Тройка рулит. Медленнее и капризнее — поэтому только там, где иначе
нельзя.

## 3. Что строим — по компонентам

### 3.1 PC-tools (Python, in-process в локальном gateway)

Никакого моста. Обычные локальные tools, исполняются в том же процессе, что и мозг.

- **`tools/pc_tool.py`** — прямые Windows-хендлеры (не обёртки над мостом). Хендлеры
  принимают `**_kw` (иначе registry падает — память `tool-handler-kwargs`). Первый набор:
  - `pc_open_file(path)` — открыть файл в дефолтной программе (`os.startfile`) —
    показ результата пути А
  - `pc_open_app(name)` — запустить программу (`start`/`subprocess`, реестр известных
    приложений + `where`)
  - `pc_gui_control(action, ...)` — click/type/screenshot/hotkey (путь Б), pyautogui +
    pywinauto/UIAutomation
  - `pc_run(cmd)` — базовое: громкость, свернуть окна, скриншот, буфер обмена
- **Windows-специфика.** Всё исполняется локально: `os.startfile`, `subprocess` (стримить
  долгие CLI в файл, не в PIPE — память `windows-subprocess-no-pipe`), pyautogui/pywinauto
  для GUI. Гейт на живое управление (подтверждение перед кликами в чужих окнах) — опция.
- **Регистрация в 4 местах** (память `hermes-tools-registration`): shim-файл для
  `tools/registry`, `toolsets.py` (новый toolset `pc` + ключевые в `troika-voice`), схемы,
  find_tool-описания с синонимами (падежи!).
- **Доставка файла — тривиальна.** file-gen tools (`pptx`, `docx`, `xlsx`) кладут файл в
  vault локально. Раз всё на одной машине — мозг просто зовёт `pc_open_file(<путь>)`.
  Никакого скачивания по `/v1/files` не нужно.

### 3.2 Local PC Executor — НЕ НУЖЕН в local-first

Отдельный исполнитель/sidecar с WebSocket требовался бы, только если мозг на удалённом
сервере. Здесь мозг локальный, поэтому исполнение живёт прямо в `tools/pc_tool.py`
(см. 3.1). Пункт оставлен как маркер: вернётся, если позже вынесем мозг в облако.

### 3.3 Flutter Windows app (клиент, оболочка)

`windows/` уже есть — десктоп включён. Переиспользуем `hermes-android/lib` максимально.

- **Общий код без изменений:** лента чата, `hermes_api_service.dart` (HTTP к gateway,
  SSE-мысли), `files_service.dart`, тема, виджеты. Мозг и транспорт те же.
- **Заменить платформенное (Android-специфику) на десктопное:**
  - **STT** — сейчас через Android/Whisper-proxy. На ПК: слать аудио на тот же
    `STT_BACKEND=groq` (память `troika-stt-backend-groq`) через микрофон Windows
    (`record` уже кроссплатформенный) — фактически можно переиспользовать текущий поток.
  - **TTS** — серверный Edge TTS уже отдаёт MP3; на Windows просто проигрывать
    (`just_audio`/`audioplayers` desktop). Логику наложения/barge-in взять как есть.
  - **Wake-word «тройка»** — портировать на desktop (Porcupine/Vosk desktop или
    постоянный STT-стрим). Отдельная подзадача.
- **Новое в приложении:**
  - запуск/надзор за Local Executor (поднять sidecar, показать статус «ПК под
    управлением: вкл»),
  - onboarding под Windows (микрофон, автозапуск, путь к серверу+ключ — по образцу
    `troika-app-onboarding`).

## 6. Риски / грабли (из памяти)

- Новый tool обязан попасть в `toolsets.py`, иначе LLM его не увидит (аудит tools).
- Хендлеры без `**_kw` → registry TypeError.
- Долгие CLI на Windows: стримить в файл, не в PIPE (зомби-задачи иначе).
- `find_tool` без лемматизации — синонимы с падежами могут не находиться; описания tools
  писать с синонимами.
- Живое GUI-управление медленно/хрупко — держим его как запасной путь, не как основной.
- Windows desktop STT/TTS/wake-word — отдельная реальная работа, не «бесплатно из
  Android».
