# План улучшений Тройки

Документ для Миши. Три части: что уже сделано в этой ветке, глобальные улучшения
существующих инструментов, и новый блок — безопасность и атака.

Ветка: `troika/anti-confusion-and-brain`

## Часть 0. Что уже сделано (готово к деплою)

### Мозг — бесплатный апгрейд (Фаза 1, рецепт)
Сейчас мозг = Groq `llama-3.3-70b`. Более умная **бесплатная** замена, доступная
прямо сейчас на том же ключе: **`openai/gpt-oss-120b`** через Groq.

⚠️ **Сначала проверить живьём.** На OpenRouter `gpt-oss-120b:free` = 8k контекст и
тупит (Миша пробовал 22.06). На **Groq** та же модель должна идти с полным
контекстом и 30k TPM — но это надо подтвердить тестовым запросом на ключе Миши
ПЕРЕД заменой `llama-3.3-70b`. Если Groq режет контекст — остаёмся на 70B.

Почему она (если проверка прошла):
- 120B MoE с **reasoning + tool calling** — заметно умнее 70B, держит длинный
  контекст и сложные цепочки рассуждений лучше (меньше «тупит»).
- Groq сам перевёл флот на неё, задепрекейтив `kimi-k2` (23.03.2026) и
  `qwen3-32b`/`llama-4-scout` (17.06.2026) — значит она поддерживается долго.
- Free tier: **30k TPM** (против старого лимита 6k, на котором DAEMON ловил 413).
- **Кешированные токены не считаются в лимит** — а после Фазы 2 у нас стабильная
  личность отдельно от волатиля → prompt caching реально продлевает free tier.

Как включить (host `.env` на сервере, `/root/troika/.env` или `/opt/data/.env`):
```
# мозг = gpt-oss-120b через Groq (provider:custom, как в troika-brain-groq-custom)
LLM_MODEL=openai/gpt-oss-120b
```
И в `config.yaml` / model_aliases (как уже настроен Groq-custom):
```yaml
model_aliases:
  brain:
    model: openai/gpt-oss-120b
    provider: custom
    base_url: https://api.groq.com/openai/v1
```
⚠️ Не указывать лишних ключей в model-блоке (иначе «multiple values for model»).
Рестарт: `/command/s6-svc -r`. Откат — вернуть `llama-3.3-70b`.

### Память по релевантности (Фаза 2, код в ветке)
Корень «мозг путается, когда всё в одном месте» был не в хранении (оно как раз
разнесено: SOMA / diary / vault / sessions), а в **сборке промпта**:
`soma_context_hint` дампил топ-6 выводов о Мише в КАЖДЫЙ запрос, слипшись с
личностью в кешируемом system prompt. Слабая модель путала «вечный фон о Мише» с
текущей задачей.

Сделано:
- `soma_context_hint(query=...)` ранжирует по релевантности к реплике; не
  относящиеся выводы отбрасываются. «Который час» больше не тащит досье на Мишу.
- SOMA вынесен из стабильной личности (`load_soul_md`) в волатильный слой —
  память отделена от идентичности.
- Пороги ужесточены (confidence 0.45→0.55, лимит 6→3), всё за env-флагами:
  `SOMA_CONTEXT_LIMIT`, `SOMA_CONTEXT_MIN_CONF`, `SOMA_CONTEXT_MIN_REL`,
  `SOMA_CONTEXT_DISABLED`. Полностью откатываемо.

## Часть 1. Глобальные улучшения существующих инструментов

Приоритет по влиянию на «не путается / не тупит».

### 1.1 Per-turn инжект памяти (продолжение Фазы 2) — ВЫСОКИЙ
Сейчас SOMA фильтруется по **первой** реплике сессии (промпт кешируется на
сессию ради Groq TPM). Для голосовых сессий «одна тема за сессию» это почти
всегда верно, но для длинных текстовых диалогов память «застывает» на первой
реплике.
**Что сделать:** инжектить релевантную память не в system prompt, а в ephemeral
hint перед каждым turn'ом, с динамическим prompt-кешем (кешировать стабильный
префикс отдельно от per-turn хвоста). Это окончательно убирает «застывание» без
потери TPM-экономии.

### 1.2 Лемматизация в `find_tool` и SOMA-релевантности — ВЫСОКИЙ
Из аудита: `find_tool` без лемматизации не находит синонимы в падежах
(«сделай ролик» vs «сделать видео»). Та же проблема у новой SOMA-релевантности:
токены сравниваются как есть, «ночью»≠«ночь».
**Что сделать:** лёгкая стемминг-нормализация русских токенов (pymorphy/снежок
или простой суффикс-stripper) в общем `_tokens`. Поднимет точность и роутинга
инструментов, и подмешивания памяти.

### 1.3 Единый бюджет контекста (token budget) — ВЫСОКИЙ
Сейчас в промпт льются независимо: SOUL, SOMA, skills index, env/platform hints,
tool-payload. Никто не считает суммарный бюджет — отсюда 413/429 на лимитах.
**Что сделать:** ввести верхний бюджет токенов на system prompt; при превышении
ужимать в порядке приоритета (личность > релевантная память > skills index >
hints). Логировать, что ужалось. Это системное лекарство от «захлёбывания».

### 1.4 Skills index по релевантности, а не «mandatory все» — СРЕДНИЙ
«Перед ответом просканируй ВСЕ скилы» — шум для слабой модели. Механизм
`_skill_should_show` уже есть; добавить ранжирование по релевантности к реплике
(как у SOMA) и показывать топ-N, а не весь индекс.

### 1.5 IRIS/response_flow/time hints — собрать в один компактный блок — СРЕДНИЙ
Сейчас 4 отдельных хинта клеятся к SOUL по очереди. На слабой модели это 4
конкурирующих «голоса». Свести в один короткий блок «текущий контекст момента».

### 1.6 Наблюдаемость промпта — НИЗКИЙ, но полезный
Tool `prompt_inspect`: показать, из чего собран текущий system prompt и сколько
токенов съел каждый слой. Чтобы видеть, где раздувается, а не гадать.

## Часть 2. Новое в безопасности и атаке

Сейчас весь security у Тройки **оборонительный** (path_security, threat_patterns,
tirith — защита от prompt injection). Наступательного/recon инструментария нет.
Это легитимный пробел для авторизованного пентеста / CTF / своей инфры.

> Рамки: всё только для **своих** систем, авторизованного тестирования, CTF и
> обучения. Каждый наступательный tool обязан требовать явного подтверждения цели
> (own-asset / authorized) и логировать, что и по какой цели запускалось.

### 2.1 `recon` — пассивная разведка своей инфры — ВЫСОКИЙ
Голосом «проверь мой сервер / что открыто наружу». Обёртка над:
- порт-скан своего хоста (nmap/`-sV` по своему IP, с гейтом own-asset),
- TLS/cert-проверка (срок, цепочка, слабые шифры),
- заголовки безопасности HTTP (HSTS, CSP, X-Frame),
- DNS/субдомены своего домена.
Выдаёт человеку короткий отчёт «что торчит и что чинить». Не блокирует диалог
(через job_runner, как gemini_code).

### 2.2 `secrets_audit` — поиск утёкших секретов — ВЫСОКИЙ
Сканер своего репо/папки на ключи, токены, пароли в коде и истории git
(паттерны как у threat_patterns, но для исходящих утечек). Голосом «нет ли у
меня где ключей в коде». Прямо дополняет уже существующий `secrets_audit`-пробел
из аудита tools.

### 2.3 `harden` — чек-лист укрепления — СРЕДНИЙ
По результатам recon — конкретные шаги: закрыть порт, включить fail2ban,
обновить пакеты с CVE, ужесточить sshd_config. Не делает сам без подтверждения,
но готовит команды и объясняет риск.

### 2.4 `cve_watch` — мониторинг уязвимостей зависимостей — СРЕДНИЙ
Раз в день (через cron, уже есть) проверять зависимости проектов Миши против
свежих CVE (osv.dev / GitHub advisories) и пушить в Telegram, если что-то
горит. Проактивно, в духе DAEMON.

### 2.5 `ctf_assist` — помощник для CTF/обучения — НИЗКИЙ
Песочница для разбора задач: декодеры (base64/hex/rot/JWT), crypto-хелперы,
анализ бинарей (strings/file/objdump-обёртки), reverse-подсказки. Чисто
обучающее, без действий по чужим целям.

### 2.6 Усиление обороны (то, что уже есть) — ВЫСОКИЙ
- **Egress-контроль для под-агентов:** claude_code/gemini_code сейчас могут
  ходить в сеть свободно. Добавить allowlist доменов для кодеров.
- **Песочница на самоулучшение:** self_improve уже проверяет в песочнице, но
  стоит добавить статический скан diff'а на бэкдор-паттерны перед апрувом.
- **Аудит-лог наступательных действий:** отдельный неизменяемый журнал, что и по
  какой цели запускалось — для own-asset подтверждения постфактум.
