# Диагностика управления телефоном и времени ответа

Проверка 18 ноября 2026 года. Время ниже — Москва (UTC+3).
Источник: production agent/errors logs, audit events, метаданные вызовов
и учёта расхода; исходники текущего checkout и конфигурация контейнера.
Содержимое разговоров и секреты в отчёт не включены.

## Подтверждённый сценарий

18 ноября в 09:12:20 начался запрос; финальные диагностические события
записаны в 09:12:33. Последовательность:

1. `troika_tool_search(capability=phone)` — успех.
2. `troika_tool_call(tool=android_open_app)` — `app_not_found`, 10,06 с.
3. `troika_tool_search(capability=screen)` — `capability_unavailable`, 0,02 с.
4. Текстовый ответ модели; вызова `troika_device_control` не было.

`phone` предоставляет базовые команды. `screen` относится к отдельному
режиму снимка экрана, который в production выключен.
Для чтения элементов, нажатий, ввода и прокрутки существует `control`.
Его серверный флаг и настройка пользователя включены; файл инструмента
присутствует в текущем образе. Модель в проверенном запросе выбрала другие
возможности. Отказ `screen` не доказывает недоступность `control`.

Телефон подключался к каналу в 09:10:45 и 09:11:41 и вернул прикладную ошибку
в 09:12:32. Связь в момент команды работала. Почему имя приложения не
найдено, по этим данным не установлено. В текущем `findPackage` используется
package name и совпадение с label; комментарий об алиасах не соответствует
реализации. Установленную APK и список приложений по USB проверить нельзя:
подключённых устройств нет.

## Откуда время ожидания

Четыре LLM-операции последнего запроса закрылись за 0,70 / 0,55 / 0,44 /
0,63 с по меткам учёта. Использовалась тарификация бесплатной модели;
провайдер сообщил 0 reasoning tokens. Большая часть общего времени пришлась
на вызов открытия приложения. Его длительность включает возможное ожидание
пользовательского approval; отдельной длительности исполнения на устройстве
в исследованных записях нет. Причину всей задержки нельзя приписать телефону.

Вечером 17 ноября зафиксированы `tool_not_allowed`, `unknown_capability` и
серия `invalid_tool_arguments`; есть успешные базовые команды телефона.
В 22:49:33 `phone` был недоступен, затем подключение восстановилось в 22:49:44.
Это отдельный кратковременный разрыв, а не доказательство постоянного отказа.

Утром 18 ноября три LLM-операции с тарифной записью Pro DeepSeek остались
в состоянии `dispatched`, без usage и финального списания. Следующий
успешный запрос использовал бесплатную модель. Причина ошибок Pro и
корректность сверки неизвестного расхода требуют отдельной проверки.
Предупреждения об отсутствии Nous auth есть, но они не доказывают задержку
основной модели и не означают подтверждённый долг OpenRouter.

## Исправления и развёртывание

После первичной диагностики владелец поручил исправить найденные проблемы.
USB-телефон SM-A225F подключился, доступ по SSH восстановился.

- Разделены инструкции для базовых Android-команд, отдельного screenshot
  и управления элементами. Отсутствие `screen` не закрывает доступный `control`.
- Текущая просьба и авторизованное устройство определяют назначение команд.
  Нельзя выбрать другой онлайн-ПК из истории или подменить выключенный телефон.
  При неоднозначном назначении действие не выполняется.
- Android-команды отклоняют неизвестные аргументы и возвращают ожидаемые поля.
  Одинаковый ошибочный вызов блокируется после двух неудач; изменённые аргументы
  можно попробовать. Защита установлена и на фактически работавшем старом core.
- Общий Android resolver распознаёт установленные приложения по package id,
  русским/английским алиасам и однозначному названию. Произвольное вхождение
  названия в длинную фразу больше не запускает случайное приложение.
- Подтверждённый OpenRouter HTTP 402 до получения ответа закрывает резерв с
  нулевым расходом. Таймауты, 5xx, неизвестный расход и ошибки внутри стрима
  по-прежнему останавливают повтор; старые резервы не пересчитывались.
- Вторая живая проверка показала `Fallback to openrouter failed: provider not
  configured`: основной ключ был разрешён gateway, но не передавался fallback.
  Теперь запасная модель того же hosted-провайдера получает его runtime key и
  endpoint. Пользовательские тарифы и политика Plus/Pro не изменены.

Проверка реального провайдера: баланс OpenRouter ниже нуля примерно на $0,20;
запрос Pro с обычным пределом 8192 tokens получил 402 за 0,34 с. Запрос с
пределом 8 tokens ранее проходил. Эти наблюдения подтверждают проблему
доступного лимита для текущих запросов, но не доказывают причину каждой старой
незавершённой операции. Ответы/ключи/сообщения пользователей в аудит не включены.

## Живая проверка

Владелец повторил команду открытия настроек. С Free сервер действительно
нашёл `control` и вызвал `troika_device_control`; получил `plus_required`,
что соответствует политике Plus/Pro. Затем владелец вошёл в Pro и получил
ошибку отсутствующего fallback credential; исправление установлено второй
сборкой. После второй сборки живой Pro-запрос: отказ premium закрыт как
settled/unsuccessful; далее пять успешных бесплатных LLM-операций по 0,60–1,19 с.
Fallback работает. Был один guessed tool_not_allowed, затем модель загрузила
инструмент и вызвала control. Ответ — `device_not_connected`, без подмены на ПК.

Код NativeAccountSession.invalidate отключает локальный phone control при
выходе. После перехода Free → Pro владелец должен заново включить
«Настройки → Разрешения → Команды Тройки на этом телефоне» и иметь Android
Accessibility permission. Владельцу переданы эти шаги и запрошен USB для
диагностики, если связь не восстановится. Фактическое локальное значение
после смены аккаунта по USB пока не прочитано. Успешное управление экраном
и Stop ещё не подтверждены; скорость всей цепочки не измерена.
