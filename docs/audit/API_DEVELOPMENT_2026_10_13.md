# Разработка и ревью через API — 13 октября 2026

По запросу владельца основной режим разработки заменяет обязательные проверки
телефона/ПК циклом через API. У прежнего пути `troika_create_project` был только
упаковщиком: основной агент должен был написать весь проект в одном вызове.
Теперь параметр `task` запускает требования, план, запись каждого файла,
независимое ревью всех исходников и до трёх исправлений с повторным ревью.
Существующие файлы сначала проверяются; работающие файлы сохраняются.

## Реализация и границы

- `troika_product/development_agent.py` использует центральный `call_llm`.
  Запись: `auxiliary.development`, OpenRouter `qwen/qwen3-coder-next`.
  Ревью: `auxiliary.development_review`, OpenRouter `openai/gpt-5.4-mini`.
  Оба маршрута настраиваются на сервере; основной чат не меняется.
- JSON Schema задаёт формат планов, файлов и отчётов. Дополнительная проверка
  отвергает обрезанный JSON и неполное покрытие файлов. Повтор получает конкретную
  причину отказа. Для замечания нужны точная строка исходника и сценарий с
  ожидаемым и предполагаемым результатом. Строка вычисляется runtime.
- 40 файлов, 160 000 байт сериализованного JSON-контекста, 64 API-вызова,
  15 минут на цикл. При превышении нет частичного положительного ревью.
- Stop проверяется между вызовами и перед передачей. Identity/owner/device,
  ограничения путей и запрет передачи обнаруженных ключей сохранены.
  Пакет без `task` не может приложить доверенное ревью из аргументов модели.
- ZIP содержит реализацию, README, тесты, REQUIREMENTS.md, PLAN.md,
  MODEL_REVIEW.md и manifest. `execution=not_run` обозначает ревью без исполнения.
  Синтаксис Python/JSON проверяется статически. На облачном host исходники не
  запускаются и постоянная копия готового проекта не создаётся.
- Android и WPF по умолчанию выбирают «Модель: ревью и исправление».
  Выбор устройства и разрешение запуска нужны только для отдельной локальной
  проверки. Исходное назначение веб-приложения сохраняется; Python/CommonJS
  больше не являются обязательным стеком основного режима.

Поддержка Structured Outputs сверена с [OpenAI Docs](https://developers.openai.com/api/docs/models/gpt-5.4-mini)
и [документацией OpenRouter](https://openrouter.ai/docs/guides/features/structured-outputs).
Это платные API-маршруты. При включённом ресурсном режиме цены обеих моделей
должны присутствовать в серверном каталоге; неизвестная цена не обходится.
Действующие ключи остаются на сервере. В клиенты ключи не добавлены.

## Реальный пример

Через API создан браузерный калькулятор калорий: HTML/CSS, модуль логики,
контроллер, тесты настоящего модуля и README. Всего девять файлов плюс manifest.
Пример не дописывался вручную. Артефакты проверки находятся локально в
`work/development-api-20261013`; пользовательские данные не использовались.

Первоначальное ревью Qwen пропускало ошибки тестового окружения и повторяло
уже исправленные замечания. Поэтому добавлены конкретные причины повторов,
проверка цитат и отдельная API-модель ревью. Финальный цикл сохранил интерфейс,
исправил тестовое окружение, логический модуль и контроллер. Один цикл
исправления, шесть API-вызовов, 273 секунды; финальное ревью не содержит
блокирующих замечаний. Один minor отмечен в отчёте: дополнительное усиление
строгого чтения числовых полей. Ревью не является гарантией отсутствия ошибок.

Дополнительная проверка разработчика на ПК, отдельно от продуктового ревью:
Node `--test test/calculator.test.js` — **33 passed, 0 failed**, exit 0.
В браузере проверены синтетические значения:

- 200 ккал/100 г × 150 г = 300 ккал; 120 × 75 / 100 = 90 ккал; итог 390.
- Перезагрузка сохраняет обе строки и итог 390.
- Удаление первой строки оставляет 90; очистка оставляет 0.
- Отрицательные значения блокируются без добавления строки.

## Применение

Код и сборки готовы к проверке. Новый runtime не развёрнут; установленные
клиенты ещё используют прежний режим. До выпуска нужны согласованное обновление
API и клиентов, серверные цены моделей при включении ресурсного режима и свежий
installed-client E2E создания/исправления/Stop/передачи ZIP. Изолированные сборки
не следует устанавливать поверх клиента с незавершёнными native/reminder
изменениями без их согласованного объединения. Старые согласия и проверки
устройства остаются совместимыми.
