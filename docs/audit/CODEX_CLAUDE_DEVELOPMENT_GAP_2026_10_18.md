# Разработка Troika в сравнении с Codex и Claude Code

Дата: 18 октября 2026 года. Основа: рабочая копия `D:\troika-product`, HEAD
`a5c3b0226f6bf502cb8b37fadfe265247af8d391`, включая существовавшие до аудита
незакоммиченные изменения. Это статический аудит и предложение поведения,
а не отчёт об обновлении сервера или установленного приложения.

Владелец выделил три проблемы: разработка, непонятная сущность проекта,
перекос продукта в документы и презентации. Затем уточнил ориентир:
часть разработки должна работать как Codex и Claude Code, со skills, MCP
и плагинами. Этот документ дополняет [независимый аудит](INDEPENDENT_PRODUCT_CRITIC_2026_10_18.md).

## Главный вывод

В Troika уже есть существенная основа: создание исходников, независимое ревью,
исправления, ограниченные реальные проверки, визуальная проверка, фоновые
запуски и локальные контрольные копии. Но основной механизм разработки —
последовательность запросов на структурированный JSON с последующей сборкой
проекта. Он не предоставляет разработчику полноценную рабочую папку,
подключаемые skills и цикл вызова внешних инструментов.

Поэтому добавление ещё нескольких кнопок «плагин» не устранит главное
расхождение. Нужны связанная с проектом среда работы и доступные агенту
инструменты. Качество модели влияет на результат, но само по себе эти
отсутствующие связи не создаёт.

## Что именно сравнивается

Ориентир для работы с кодом — Codex и Claude Code, а не обычный чат.
Codex описывает работу в терминале, отдельное ревью изменений и продолжение
сохранённых разговоров. Claude Code описывает чтение существующей кодовой
базы, изменения нескольких файлов, команды, проверки и Git.
Это документированные возможности, а не утверждение об их безошибочности.
Источники: [Codex CLI](https://learn.chatgpt.com/docs/codex/cli),
[Claude Code](https://code.claude.com/docs/en/overview),
[рабочие сценарии Claude Code](https://code.claude.com/docs/en/common-workflows).

| Возможность | Ориентир Codex / Claude Code | Что подтверждено в Troika | Нужное поведение Troika |
|---|---|---|---|
| Существующий код | Работа внутри выбранной кодовой базы | Передача массива текстовых файлов; Windows импортирует ZIP; общего выбора repository нет | Открыть разрешённую папку, увидеть состав и использовать текущие файлы |
| Продолжение | Сохранённая сессия относится к работе с проектом | Есть фоновые Run и checkpoints; отдельная модель «Проекты» для дел | Одна понятная карточка связывает папку, разговоры, задачи, версии и проверки |
| Изменения | Изменения файлов можно рассмотреть и проверить | Новая сгенерированная версия и ZIP; продолжение из checkpoint | Прочитать актуальное состояние, показать изменения, применить их без потери ручных правок |
| Проверки | Агент получает результат реального инструмента | Автопилот имеет фиксированный checker; обычный tool-route возвращает `execution=not_run` | Единый понятный результат с раздельными статусами ревью, тестов, сборки и preview |
| Skills | Подключаемые инструкции и вспомогательные ресурсы | Девять встроенных capability-групп; поле `skill` содержит готовый текст | Пользовательские и проектные `SKILL.md`, явный и автоматический выбор, видимый факт применения |
| MCP | Настроенный сервер предоставляет вызываемые инструменты | Унаследованный MCP-клиент существует; в новом development API инструменты не передаются модели | Подключение сервера в контексте проекта и реальные вызовы через policy/approval |
| Плагины | Пакет может добавлять skills и MCP; у Claude также agents/hooks | Вкладка показывает встроенные capability, а не установленные расширения | Manifest, версия, установка, отключение, разрешения, зависимости и диагностика |
| Инструкции проекта | Правила проекта участвуют в работе агента | Нет загрузки `AGENTS.md`/`SKILL.md` как доверенных правил нового development workflow | Отдельно загрузить одобренные правила; различать их и недоверенный текст исходников |
| Контроль пользователя | Можно продолжать и направлять работу, видеть изменения | Пауза, уточнение, Stop и бюджет уже есть | Сохранить эти механизмы и связать их с актуальной папкой и инструментами |

Skill в Codex — каталог с `SKILL.md` и необязательными scripts/references/assets;
полный текст загружается при применении. Claude Code поддерживает проектные
и личные skills, автоматический выбор и явный вызов команды.
Источники: [skills Codex](https://learn.chatgpt.com/docs/build-skills),
[skills Claude Code](https://code.claude.com/docs/en/skills).

Codex поддерживает MCP через локальные STDIO и удалённые Streamable HTTP
серверы с вариантами авторизации. Claude Code также имеет конфигурацию
серверов по области действия, включая проект. Поддержка зависит от
поверхности и среды; наличие стандарта не даёт одному приложению доступ
к подключениям другого. Источники: [MCP Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli),
[MCP Claude Code](https://code.claude.com/docs/en/mcp).

Плагины ChatGPT/Codex могут объединять skills и MCP. Плагины Claude Code
могут также включать определения агентов и hooks. Совместимость manifest,
разрешений и всех расширений между продуктами из этого не следует.
Источники: [плагины Codex](https://learn.chatgpt.com/docs/plugins),
[плагины Claude Code](https://code.claude.com/docs/en/plugins).

## Подтверждённые причины в исходниках

### G1. Модель разработки не получает инструменты

`troika_product/development_agent.py:174–194`: `_api()` вызывает `call_llm()`
без `tools`. Сам `call_llm()` умеет принимать `tools`, но его значение
по умолчанию равно `None` (`agent/auxiliary_client.py:4787–4801`).
`DevelopmentAgent.ask()` создаёт system-инструкцию и JSON задачи, затем
разбирает `message.content` как JSON (`troika_product/development_agent.py:276–338`).
Обработки `message.tool_calls` в этом пути нет.

Автопилот использует тот же подход: `troika_product/development_team.py:89–173` вызывает
`client.chat.completions.create()` с сообщениями и схемой ответа, без `tools`.
`DevelopmentTeam` наследует `DevelopmentAgent`, добавляя планирование,
специалистов, checkpoint и checker. Checker вызывается кодом orchestration;
это реальная проверка, но не общий доступ модели к навыкам/MCP.

Вывод: специалист не сможет самостоятельно запросить MCP-инструмент,
прочитать skill через инструмент или исследовать новую папку. Добавить
название сервера в prompt недостаточно.

**Приёмка:** задача требует данные тестового MCP-сервера. Агент обнаруживает
точную схему, вызывает инструмент, использует возвращённое значение,
сохраняет проверяемый результат. Отключение сервера запрещает новый вызов.

### G2. «Навыки» и «Плагины» сейчас означают встроенные возможности

`troika_product/capabilities.py:35–65` задаёт фиксированные группы:
assistant, web, documents, development, files, phone, images, vision, screen.
`catalogue():244–252` возвращает `source="builtin"` и `skills` из `item.skill`.
В Android вкладка «Навыки» выводит этот текст
(`hermes-android/lib/screens/capabilities_screen.dart:137–140,208–212`);
на ПК три вкладки используют тот же каталог
(`troika-desktop/src/CapabilityCataloguePanel.cs:42–66`).

Сам каталог не фиктивный: обычный агент действительно может получать
схемы и инструкции через `troika_tool_search`. Но он не является каталогом
пользовательских `SKILL.md`, установщиком пакетов или менеджером MCP-серверов.
Кроме того, developer specialists не получают этот discovery/call loop.

**Приёмка:** пользователь добавляет собственный skill, видит его источник
и область действия, вызывает по имени; результат показывает применение
именно этого skill. Выключенный skill не применяется ни основным агентом,
ни специалистом. Для плагина видны manifest, версия и состав пакета.

### G3. Унаследованные расширения и hosted product — разные пути

В репозитории есть настоящий механизм skills (`tools/skills_tool.py`,
`skills_list`, `skill_view`), MCP (`tools/mcp_tool.py`,
`discover_mcp_tools`, `register_mcp_servers`) и plugin hooks
(`hermes_cli/plugins.py`). Их наличие не доказывает доступность в новом клиенте.

Продуктовый набор определяется `toolsets.py:556–569`,
`troika_product/feature_policy.py:138–145` и фильтром
`available_schemas()` (`troika_product/capabilities.py:185–216`). У него нет общего пути
установки и выдачи пользовательских MCP/skills в development specialists.
Обычный `troika_terminal` — ограниченный файловый инструмент; это не
терминал coding agent (`tools/troika_workspace_tool.py:329–338`).

**Приёмка:** один разрешённый набор расширений проекта проходит весь путь:
настройка, discovery, вызов основным агентом, вызов специалистом, отзыв.
Проверка должна использовать отдельные аккаунты и одинаковые серверные
проверки доступа для прямого вызова и вызова специалиста.

### G4. У разработки два разных пользовательских контракта

`tools/troika_documents_tool.py:161–190` запускает обычный
`DevelopmentAgent`, создаёт ZIP и явно возвращает `execution="not_run"`.
Отдельный `workflow=development` запускает `DevelopmentTeam` и checker.
Пользователь не должен угадывать, какой механизм выбрал вход через чат
или панель. Это не повод объявить первый механизм сломанным: он соответствует
прежнему ограниченному контракту. Но различие мешает ожидаемой единой разработке.

**Приёмка:** одинаковая задача из текста и из панели создаёт связанный
development Run с одинаковыми возможностями и честными статусами проверки.
Внешний кодовый проект можно открыть и доработать по произвольному заданию.

### G5. «Проект» не связан с актуальной рабочей папкой

Дела используют `/v1/assistant/projects`; development metadata хранится
отдельно в `troika_development_projects`, с owner/device scope
(`troika_product/development_sessions.py:48–65,108–132`).
На ПК Resume отправляет `checkpoint` из локального защищённого хранилища
(`troika-desktop/src/DevelopmentAutopilot.cs:132–137`). Этот путь не перечитывает
сохранённую пользователем папку. Android также продолжает из checkpoint.
Остальные разрывы импорта, восстановления папки и подписей приведены в
[независимом аудите](INDEPENDENT_PRODUCT_CRITIC_2026_10_18.md).

**Приёмка:** создать проект, изменить файл обычным редактором, закрыть Troika,
открыть проект и попросить новую функцию. Агент видит ручную правку и сохраняет
её. Перед применением изменений доступен diff; конфликт не перезаписывается
молча. Если папка недоступна, приложение объясняет состояние и просит её выбрать.

### G6. Перекос в документы существует в подаче, но не доказывает принудительную маршрутизацию

На сайте демонстрация первого экрана посвящена презентации
(`troika-site/src/content.mjs:10`). ПК ставит «Документ» и «Презентация»
рядом с «Поиск» и «Код» (`troika-desktop/src/MainWindow.cs:181`).
В автопилоте разработка объединена с генерацией DOCX/PPTX через
`output_kind` (`troika_product/development_team.py:308–310`).

При этом CORE_PERSONA не требует превращать каждый запрос в документ
(`troika_product/context_guidance.py:3–15`). Пакетирование кода в ZIP и
неполная рабочая среда объясняют часть ощущения «файловой фабрики».
Точного доказательства, что свободный запрос принудительно уходит в PPTX,
статический аудит не получил: для этого нужен сценарий владельца и свежий Run.

**Приёмка:** запрос о коде остаётся в разработке, исследование выдаёт
ответ и источники, обычный разговор не создаёт файл. DOCX/PPTX появляются
по прямому запросу или по принятому пользователем предложению.

## Как должен выглядеть понятный проект

Предлагаемый сценарий: «Открой мой проект и добавь поиск». Troika показывает
выбранный проект, его папку, активную задачу и последние проверки. Затем
читает актуальные файлы и одобренные правила, подключает нужные skills,
получает разрешённые инструменты/MCP, вносит изменения, проверяет их и
показывает результат. Следующая просьба относится к этому же проекту.

Минимальная карточка проекта содержит:

- название и назначение;
- рабочую папку и устройство, где находятся исходники;
- разговоры и задачи проекта;
- текущую версию, изменения и результаты проверок;
- доступные проекту skills, MCP и плагины;
- действия «Продолжить», «Открыть файлы», «Показать изменения», «Остановить».

Голос остаётся главным способом постановки задачи. Дерево файлов, diff,
preview и журнал проверок нужны в деталях разработки. Проекты дел могут
оставаться полезной группировкой, но их отличие должно быть явно объяснено.

## Рекомендуемый порядок реализации

Это предложение по результатам аудита. Оно не меняет молча действующий
план, доступ Pro, бесплатный маршрут моделей или правила хранения данных.

1. Исправить подтверждённые ошибки текущего UX: статусы проверок,
   произвольное задание для импортированных исходников, поддерживаемые
   расширения ZIP, сохранение связи с папкой. Показать пользователю разницу
   между делами и кодовым проектом.
2. Завершить рабочую среду проекта: выбрать существующую папку, читать
   актуальные файлы, исключать секреты, готовить изменения и применять их
   с проверкой конфликтов. Связать Run, разговор и локальную версию.
3. Добавить runtime skills: каталог metadata, загрузку `SKILL.md`, ресурсы,
   правила выбора и явный вызов. Наличие skill не должно давать новых прав.
4. Добавить цикл инструментов разработки: discovery, вызов, результат,
   продолжение, бюджет и Stop. Подключить MCP к тому же контролю доступа.
5. Добавить пакеты плагинов и hooks поверх уже работающих skills/MCP.
   Указать поддерживаемые форматы; не обещать совместимость со всеми
   расширениями других продуктов.
6. Проверить общий сценарий на установленном Android и Windows, включая
   ручное редактирование, продолжение, отключение расширения и потерю сети.

Облачный API остаётся orchestrator. Локальные инструменты и STDIO MCP
требуют разрешённого исполнителя на устройстве; фиксированный серверный
checker сохраняет согласованные границы. Новые scripts/hooks не становятся
автоматически разрешёнными командами на production host.

## Что проверено и что остаётся неизвестным

Прочитаны согласованные планы и исходники перечисленных путей. Отдельная
проверка Python AST подтвердила отсутствие аргумента `tools` у двух
development API-вызовов и отсутствие обработки `tool_calls` в `ask()`.
Каталог содержит девять фиксированных capability. Была выполнена машинная
инвентаризация 306 файлов и 2 843 Python-функций; это не ручное ревью каждой
из них. Точные границы и хеши находятся в
[покрытии](INDEPENDENT_AUDIT_COVERAGE_2026_10_18.json), определения Python —
в [индексе функций](INDEPENDENT_FUNCTION_INDEX_2026_10_18.csv).

Новый model/provider E2E, тесты всех расширений, проверки установленного
клиента и полный regression suite в рамках этого аудита не запускались.
Код продукта и production не менялись. Существующие результаты тестов из
памяти проекта не переобозначаются как результаты этого аудита.
