# Локальный прототип управления Windows

Третий шаг плана внедрения проверяет настоящий Windows UI Automation в
собственном тестовом редакторе WPF. Проба запускается отдельным ключом
`--computer-use-prototype` до загрузки профиля и обычного клиента.

## Сценарий

Окно показывает цель пробы и две кнопки для владельца. «Разрешить и запустить»
выдаёт разрешение на 120 секунд. «Остановить», Escape или закрытие окна отзывают
его на ПК. Таймер работает на монотонных часах. Повторное согласие в том же окне
не открывает закрытый сеанс.

Исполнитель по UI Automation находит только собственное окно по дескриптору,
процессу и уникальному идентификатору. Он осматривает поле редактора, вызывает
запись фиксированного образца, перечитывает поле и вызывает сохранение. Обработчик
каждого действия проверяет одноразовое разрешение непосредственно перед изменением.
Это закрывает запоздавшие вызовы UI Automation после Stop. Успешный результат
требует совпадения байтов сохранённого файла с образцом. Файл создаётся по новому
временному пути. Если файл уже существует, попытка завершается без перезаписи.

Вызовы UI Automation идут на отдельном рабочем потоке, а Stop обрабатывается
диспетчером окна. Так диспетчер может отозвать разрешение, пока ожидается
результат UI Automation. [Рекомендации Microsoft для .NET Framework](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-threading-issues).

## Границы и проверки

Пять целевых проверок прошли на Windows. Они покрывают согласие, порядок действий,
повтор, истечение срока, настоящее сохранение и чтение файла, Stop перед
запоздавшим вызовом, отказ от перезаписи и отказ при подмене идентификатора окна.
Приёмка Stop проверяет, что уже записанный в редактор текст остаётся, а новый файл
после отзыва разрешения не создаётся. Проверки используют синтетический текст.

Полная сборка WPF с `troika-desktop/build.ps1 -Test` прошла. Отдельно прошли три
проверки очереди речи. Первый запуск набора завершился на существующей проверке
длинного имени файла из-за длинного пути `TEMP`. Повтор прошёл с короткой
изолированной папкой. Голосовые ресурсы проверены локально по закреплённым хешам.
Результаты общего набора Python записаны для `c038b5b` в предыдущем отчёте.
Текущая поставка затрагивает исходники WPF, сборку WPF и документацию.

Для первой пробы выбран собственный тестовый редактор WPF. Сценарий с Блокнотом
относится к следующей проверке внешних окон. Интеграция с устройствами, очередь
удалённых команд и временная передача осмотра модели остаются отдельными этапами.
Прототип работает локально с фиксированным образцом и показывает статус в окне.
Настройки production и установленные клиенты не затронуты.

## Отдельные команды исполнителя

Локальный исполнитель принимает осмотр, запись текста и сохранение по отдельности.
Осмотр сообщает только доступные действия и создаёт одноразовый идентификатор на
15 секунд. Запись и сохранение сверяют актуальное состояние редактора. После записи
сохранение требует нового осмотра. Текст команды ограничен 512 единицами UTF-16 и
проверяется перед вводом. Запись меняет поле, а сохранение подтверждает файл по
его байтам. Сценарий демонстрационного окна использует те же команды с образцом.

Шесть целевых проверок и полный набор WPF с `build.ps1 -Test` прошли. Новый тест
передаёт отдельный текст, проверяет, что ввод сам по себе не создал файл, и
подтверждает сохранение после нового осмотра. Просроченный осмотр отклоняется
также в обработчике окна, если действие успело встать в очередь. Тесты ожидали
готовности окна перед запуском сценария UI Automation.

При технической пробе Windows 11 Блокнот восстановил старые вкладки вместе с
тестовым файлом. Проверка остановлена на этапе осмотра, до записи и сохранения.
Имена вкладок в отчёт не перенесены. Для подключения Блокнота требуется отдельное
тестовое окно, которое не восстанавливает пользовательскую сессию. До чтения
элементов нужно проверить, что окно содержит ровно один согласованный документ.
Модель пока не подключена к локальным командам.
