# Troika 0.1: продолжение диагностики и проверка подтверждений

23 октября 2026 года. Исходная ревизия — `a3b1ba4`, рабочая ветка —
`codex/product-foundation`. Production, конфигурация маршрута и установленные
приложения не изменялись. Пользовательский WIP сохраняется отдельно от commit.

## Что подтвердилось

Предыдущая [диагностика задержки](TROIKA_0_1_LATENCY_2026_10_22.md) остаётся
источником живых измерений. Новых живых серий с ключом OpenRouter не выполнялось. Текущее
состояние тестового ключа не позволяет обосновать платную серию. Публичный
каталог и endpoints проверены только GET-запросами. Наличие endpoint со статусом
доступности не доказывает успешность будущего inference-запроса.

Недостаток средств, ограничения бюджета и rate limits — разные причины отказа.
Отрицательный баланс может блокировать даже бесплатные модели. Причина
предыдущего Qwen HTTP 429 остаётся неизвестной: тело/metadata не сохранялись.
Нельзя задним числом объявлять этот 429 доказанным следствием баланса.
Источник: [OpenRouter limits](https://openrouter.ai/docs/api_reference/limits).

Как резерв для следующей ограниченной проверки подготовлены GPT-4.1 Nano и
Gemini 2.5 Flash Lite: текущая каталожная цена обоих — $0,10 за миллион входных
и $0,40 за миллион выходных токенов; заявлены tools и tool_choice. Это только
кандидаты, без подтверждённого качества русского или инструментов на данном
ключе. Default остаётся `openrouter/free`; платный fallback не добавлен.
Источники: [каталог](https://openrouter.ai/api/v1/models),
[Nano](https://openrouter.ai/openai/gpt-4.1-nano),
[Flash Lite](https://openrouter.ai/google/gemini-2.5-flash-lite).

## Итоговый ответ при исчерпании шагов

`handle_max_iterations` обходит обычный transport и самостоятельно собирает
запрос сводки. Поэтому прежняя правка профиля не охватывала этот путь:
явный disabled/low терялся при `supports_reasoning=False`, включая повтор
после пустой сводки. Конечный JSON SDK через MockTransport воспроизвёл дефект:
обычный вызов содержал настройку, сводка — нет. До правки: 4 failed, 5 passed.

Минимальная правка в `agent/chat_completion_helpers.py` разрешает зарегистрированному
provider profile заполнить отсутствующий reasoning для явной настройки.
Новый список моделей или провайдеров не добавлен. Автоматические defaults,
уже настроенные ветки и LM Studio сохраняют прежнее поведение. Маршрутизация,
лимиты, retries и metering не меняются. Отдельные проверки подтверждают два
receipts при разрешённом повторе и сохранение резерва с остановкой при
неизвестном usage. Это проверка формы запроса и поведения, а не новый замер
задержки OpenRouter.

## Поисковая выдача и прочитанные страницы

Прежний `CompletionEvidence` считал успешный `web_search` доказательством
чтения страницы. Реальный формат SearXNG receipt воспроизводил ложное разрешение
даже с пустым `data.web`. До правки отдельные проверки дали 13 failed, 16 passed.

Подтверждения разделены: `search_results/read` для непустых результатов поиска
и `information/read` для реально полученного содержимого страниц. Пустой поиск,
ошибка и явный отрицательный флаг успеха не подтверждают чтение. Непустой title или
description с URL подтверждает наличие поискового результата, а не полный
текст страницы. Capability guidance теперь явно объясняет эту границу модели.
Проверяются прямые и routed receipts, включая untrusted envelope.

Это существующая детерминированная защита с ограниченным словарём формулировок.
Она не является семантической проверкой произвольного текста, не устанавливает
соответствие каждой фразы отдельному URL и не доказывает чтение всех найденных
страниц. Присланные пользователем статьи/текст без заявления о внешнем доступе
сохраняют прежнее поведение. Старый частный false positive для формулировок о
«присланном тексте страницы» отдельно не исправлялся.

SearXNG выполняет поиск и возвращает snippets. В текущем metered runtime
`web_extract` ограничен отдельным pricing/provider gate; эта задача не открывает
новый reader и не обходит учёт расходов. Полноценное чтение внешних страниц
в живом контуре данной проверкой не подтверждено.

## Файлы и результаты проверок

Отдельный изолированный harness выполнил настоящий AIAgent tool loop:
discovery, вызов DOCX tool и итоговый ответ. Использованы три заранее заданных
SDK-ответа с синтетическим usage; настоящих вызовов провайдера и поиска — ноль.
Двенадцать loopback HTTP-запросов проверили owner/device guards, отказ неверному
токену, создание настоящего DOCX, download, соответствие size/SHA-256,
запись временного файла с flush/fsync, повторное чтение и структуру OpenXML.
Только после сохранения harness отправил ACK; затем download вернул 404,
pending list и RAM store стали пустыми. Постоянного серверного DOCX нет.

Это тестовый HTTP-клиент, а не установленный Android/WPF. Word не открывался,
визуальная вёрстка не проверялась. Успешный генератор, HTTP download, сохранение
тестовым harness и подтверждение установленного приложения — разные уровни
доказательства. ACK удаляет RAM-передачу; сам по себе bodyless ACK не доказывает
физическое сохранение и открытие файла клиентом.

После правки итогового ответа 199 целевых проверок прошли, включая 16 новых
summary-проверок, transport parity, wiring, provider profiles, LM Studio и
metered runtime. После разделения web receipts все 29 новых проверок прошли.
Старые gateway-проверки текста также удерживают ложную фразу, но два их случая
падают на устаревшем ожидании отсутствующего callback. Сам guard теперь передаётся
callback; исходник gateway в этой задаче не менялся. Это не зелёный общий набор.
Полный доступный прогон одной зафиксированной ревизии перед последней узкой поправкой завершён: 1267 файлов, 24958 passed, 575 failed, 205 skipped, 1 error по распознанным summaries. Исходники runtime и двух новых тестов совпали по SHA-256 до и после прогона. Это полный доступный default-набор; integration/e2e/docker требуют своих сервисов и по умолчанию исключены. Ещё 38 файлов завершились ненулевым кодом без распознанного summary; число тестов для них не выдумывалось.

После него исправлена одна строка сопоставления описания файла: слова «результаты поиска» и snippets в названии/описании созданного или обновлённого файла не должны требовать подтверждения чтения страницы. Три новые проверки до этой поправки дали 3 failed/29 passed. Для окончательного исходника повторён целевой поднабор: 19 файлов, 372 passed, 0 failed.

В общем прогоне новый summary-тест завис на скачивании таблицы токенизатора. Причина подтверждена отдельной offline-проверкой, блокирующей запрос до сети. Его обвязка исправлена отдельно: подменён только локальный diagnostic token estimate, DNS и socket подключения явно запрещены; SDK остаётся на MockTransport. Условия резервов и provider receipts в metering не подменяются. Для остальных целевых проверок таблица токенизатора взята из имеющегося локального cache и проверена по ожидаемому SHA-256 установленной библиотеки; загрузки из сети нет. Это изоляция тестов, а не исправление холодного cache на production.

Финальный целевой набор включает 16 summary и 32 web-проверки. Полный набор целиком после этих поправок не повторялся; его счётчики и целевые счётчики нельзя складывать. Общий набор остаётся красным; не все причины отказов установлены. Ранее смешанный прогон не является чистым сравнительным baseline.

[Численные результаты и состав проверок](data/TROIKA_0_1_GUARDS_2026_10_23.json)
сохранены отдельно от исходных живых замеров. Цель 2,5 с и десять физических голосовых E2E этим
offline-прогоном не закрываются. Для следующего живого сравнения необходим
пригодный тестовый ключ; для приёмки клиента — устройства и отдельный тестовый
контур. Production в рамках задания не используется.
