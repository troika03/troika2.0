# План: второй «рабочий стол» Тройки — Kali-окружение

Документ для Миши. Изолированное Kali-окружение на сервере, которым Тройка
пользуется голосом — как отдельное рабочее пространство, отдельно от основного.

**Назначение:** авторизованный пентест своих систем, recon, работа с
security-инструментами, CTF/легальные полигоны. НЕ для атак на чужие цели без
разрешения (ст. 272–274 УК РФ).

**Тип:** консольное окружение (без GUI). GUI-стол (VNC) сознательно НЕ берём:
лишний открытый порт, тяжёлый X-сервер, больше поверхности атаки, медленнее.
Для агента, работающего командами, графика — балласт. Минимальная поверхность =
правильно и безопасно.

**Обучение Тройки (уже сделано):**
- skill `security-methodology` (`skills/security/security-methodology/SKILL.md`)
  — методология пентеста по фазам (как работает security-компания, не «потыкал
  nmap»). Грузится когда Миша просит проверить безопасность/просканировать.
- база знаний `security/security-knowledge-base.md` в vault — инструменты по
  задачам + источники для самообучения (OWASP, HackTricks, ATT&CK, полигоны).
  Тройка достаёт детали через `memory_search`.
⚠️ При деплое: skill должен попасть в синк (`~/.troika/skills/`) и в индекс
skills; новый tool `workspace` — в 4 места регистрации (registry, toolsets.py,
troika-voice, voice-task-routing). Иначе LLM их не увидит.

**Где:** Docker-контейнер на том же VPS, что и Тройка (89.208.105.187).

---

## Хорошая новость: фундамент уже есть

Docker-backend Тройки (`tools/environments/docker.py`) уже security-hardened и НЕ
требует переписывания:
- `--cap-drop ALL` — контейнер без лишних привилегий ядра.
- `--security-opt no-new-privileges` — нельзя поднять права внутри.
- лимиты PID/CPU/памяти/диска.
- `_HERMES_PROVIDER_ENV_BLOCKLIST` — **API-ключи Тройки (Groq и пр.) НЕ
  пробрасываются** в контейнер. Твой главный страх «чтобы не палился API»
  закрыт на уровне backend'а: ключи остаются у Тройки, в Kali не утекают.
- `--network=none` доступен как опция (для allowlist-режима в будущем).

Тройка уже умеет направлять терминал в docker-backend через `TERMINAL_ENV=docker`.
Значит задача — НЕ новый backend, а: Kali-образ + слой управления + гейт целей.

## Что нужно построить

### 1. Kali-образ (на сервере, один раз)
Собрать/взять образ на базе `kalilinux/kali-rolling` с нужным набором:
- `kali-linux-headless` (метапакет без GUI) или точечно: nmap, sqlmap, nikto,
  gobuster, hydra, netcat, whois, dnsutils, curl, masscan, ffuf.
- непривилегированный пользователь внутри (privilege-drop, как ожидает
  docker-backend через `--user`).
- персистентный том для рабочих файлов Тройки (`/work`), чтобы результаты
  переживали пересоздание контейнера.

### 2. Tool `workspace` — переключение голосом (код, в ветку)
Новый tool (`tools/workspace_tool.py`), регистрируется в `toolsets.py` и
`troika-voice` (иначе LLM не увидит — см. правило 4 мест регистрации):
- `workspace_enter(name="kali")` — переключить терминал Тройки на Kali-контейнер
  (выставляет `TERMINAL_ENV=docker` + образ для текущей сессии).
- `workspace_exit()` — вернуть терминал на основное окружение.
- `workspace_status()` — где сейчас работает терминал, что за контейнер, аптайм.
- Голосовые триггеры в skill voice-task-routing: «перейди в кали», «открой свой
  рабочий стол», «вернись обратно».

⚠️ Тонкость: terminal backend сейчас выбирается через env на старте процесса.
Переключение «на лету» в рамках сессии потребует прокинуть выбор окружения в
session-scoped state (`gateway/session_context.py`), а не только в глобальный env
— иначе переключится для всех сессий разом. Это главный кусок работы по коду.

### 3. Гейт целей (код, в ветку) — НЕ обязателен, но рекомендую
Поскольку цели у тебя «все» — жёсткого блокирования не делаем. Но делаем
**мягкий гейт + аудит**:
- перед запуском сетевого инструмента (nmap/sqlmap/...) Тройка фиксирует цель в
  аудит-лог (`~/.troika/kali_audit.log`): время, инструмент, цель, сессия.
- если цель — НЕ из твоего allowlist (свои IP/домены + полигоны) — Тройка вслух
  предупреждает «цель вне твоего списка, подтверждаешь авторизацию?» и пишет
  подтверждение в лог. Не блокирует, но фиксирует ответственность.
- allowlist редактируется в `~/.troika/.env` (`KALI_TARGET_ALLOWLIST=...`).

### 4. Режим «без лимитов» внутри стола (выбор Миши)
В Kali-окружении технические рамки сняты, чтобы работал ВЕСЬ арсенал, включая
инструменты, которым нужен root и сырой доступ к сети:
- **Полная сеть** (`network=True`) — выход в интернет без ограничений.
- **Привилегии** — контейнер запускается с возвращёнными capabilities
  (`--cap-add=NET_RAW,NET_ADMIN` минимум; при необходимости `--privileged`).
  Это нужно для SYN-сканов nmap, masscan, raw-сокетов, спуфинга пакетов,
  работы с интерфейсами. Без этого половина серьёзных инструментов не пашет.
- **tirith отключён для Kali-сессий** (`TIRITH_ENABLED=0` в session-env стола) —
  сканер опасных паттернов не мешает легитимным пентест-командам (`curl|bash`
  при установке тулзов, escape-последовательности и т.п.).
- **API-ключи Тройки всё равно НЕ пробрасываются** — это снимать НЕ будем,
  иначе твои ключи утекут в инструменты. Изоляция секретов остаётся.

⚠️ **Цена режима (честно):** privileged-контейнер с полной сетью на твоём VPS —
это реальная поверхность атаки. Если в Kali-окружение что-то попадёт (через
скачанный эксплойт, заражённый тул), привилегии позволяют дотянуться до хоста.
Митигация: (1) том `/work` отдельный, можно стереть; (2) контейнер пересоздаётся
с нуля из образа за секунды — не копи в нём мусор; (3) `--privileged` включать
только когда реально нужен, по умолчанию `--cap-add` точечно. Это твой осознанный
выбор ради «всё без ограничений» — фиксирую, что риск понят.

### 5. Гейт целей — единственное, что остаётся
Технические лимиты сняты, но юридическая граница — нет (ст. 272–274 УК РФ:
несанкционированный доступ незаконен независимо от того, кто нажал кнопку).
- по ТВОИМ системам и легальным полигонам (HackTheBox, TryHackMe, свои VM) —
  без вопросов, без задержек;
- по цели ВНЕ твоего allowlist — Тройка один раз переспросит «это твоё / есть
  авторизация?» и зафиксирует ответ в аудит-лог (`~/.troika/kali_audit.log`).
  Это не блокировка, а отметка ответственности — чтобы было видно, что действие
  авторизовано. allowlist в `~/.troika/.env` (`KALI_TARGET_ALLOWLIST=...`).

Сокрытие источника атаки (анонимизация ради уклонения от обнаружения) и
автоматическая работа по чужим целям без подтверждения — НЕ реализуются.

## Как это работает на практике

### Сценарий вживую (что видит и говорит Миша)

```
Миша:    «Тройка, перейди в свой рабочий стол»  (или «открой кали»)
Тройка:  «Перешла. Я в Kali, рабочая папка /work. Что делаем?»
         └─ под капотом: workspace_enter("kali")

Миша:    «Просканируй мой сервер на открытые порты»
Тройка:  (запускает nmap внутри Kali-контейнера)
         «На 89.208.105.187 открыты 22, 443 и 8642. 8642 — это твой gateway.
          Остальное закрыто. Подробнее по 22 рассказать?»
         └─ под капотом: terminal("nmap -sV 89.208.105.187") идёт В KALI,
            не на основное окружение Тройки. Цель в allowlist → тихо.
            Результат пишется в /work и в аудит-лог.

Миша:    «Всё, возвращайся»
Тройка:  «Вышла из Kali. Снова в обычном режиме.»
         └─ под капотом: workspace_exit()
```

Если цель НЕ из твоего списка:
```
Миша:    «Просканируй example.com»
Тройка:  «example.com нет в твоём списке целей. Это твоё / есть разрешение?»
Миша:    «Да, мой полигон»
Тройка:  (фиксирует подтверждение в аудит-лог, запускает скан)
```

### Что происходит при переключении (под капотом)

Терминал Тройки выбирает окружение по переменной `TERMINAL_ENV`. Сейчас она
глобальная (одна на процесс). Механизм для per-session уже есть:
`gateway/session_context.py` хранит переменные сессии в `contextvars.ContextVar`
— они **task-local**, т.е. у каждой asyncio-сессии свои, и `get_session_env`
падает обратно на `os.environ`, если не задано. Это ровно то, что нужно.

Поток переключения:
1. `workspace_enter("kali")` ставит для ТЕКУЩЕЙ сессии
   session-env `TERMINAL_ENV=docker` + `TERMINAL_DOCKER_IMAGE=troika-kali:latest`
   (через `set_session_env`, не через глобальный `os.environ`).
2. Любой следующий вызов `terminal`/`read_file`/`write_file` в этой сессии
   резолвит backend через `get_session_env("TERMINAL_ENV")` → попадает в Kali.
3. Контейнер поднимается лениво при первой команде (как уже делает
   docker-backend), переиспользуется в рамках сессии, том `/work` персистентный.
4. `workspace_exit()` сбрасывает session-env обратно → терминал снова на основном
   окружении. Контейнер можно оставить жить (для следующего входа) или остановить.

**Почему именно per-session, а не глобально:** у Тройки параллельно могут идти
разговоры (голос + текст + DAEMON-инициатива). Если переключить `TERMINAL_ENV`
глобально, ВСЕ сессии разом уедут в Kali — DAEMON начнёт писать тебе из
пентест-контейнера, фоновые задачи сломаются. Session-scoped изолирует: в Kali
только тот разговор, где ты явно попросил. Это и есть «отдельный рабочий стол»,
а не «подменили ОС всем».

### Границы изоляции (что разделено)

| Аспект                | Основное окружение Тройки | Kali-рабочий стол        |
|-----------------------|---------------------------|--------------------------|
| Файловая система      | сервер Тройки             | контейнер + том `/work`  |
| API-ключи (Groq и пр.)| есть                      | **НЕ пробрасываются**    |
| Инструменты Kali      | нет                       | весь арсенал             |
| Привилегии ядра       | —                         | privileged/NET_RAW (режим без лимитов) |
| Сеть                  | как у Тройки              | полный интернет          |
| Снести/пересоздать    | нельзя (это сама Тройка)  | за секунды, без потерь   |

Тройка не «становится» Kali — она **дотягивается** до изолированного окружения и
работает там руками, оставаясь собой (личность, память, голос — на основном
сервере). Переключение меняет только то, КУДА уходят команды терминала.

### Жизненный цикл контейнера

- **Старт:** лениво, при первой команде после `workspace_enter`. Первый раз —
  пара секунд на запуск (образ уже собран).
- **Во время работы:** один контейнер на сессию, том `/work` копит результаты
  (отчёты сканов, выкачанные файлы) между командами и входами.
- **Выход:** `workspace_exit` отцепляет терминал. Контейнер по умолчанию
  остаётся (тёплый старт в следующий раз); `workspace_status` покажет аптайм,
  отдельная команда «убери кали» — остановит и почистит (том сохранится).
- **Сброс:** «пересоздай рабочий стол» — снести контейнер, поднять заново из
  образа. Том `/work` переживает (если не попросишь стереть и его).

## Шаги на сервере (когда решишь катить)

1. **Образ.** На VPS: `docker pull kalilinux/kali-rolling`, затем Dockerfile с
   `kali-linux-headless` + privilege-drop user + том `/work`. Собрать как
   `troika-kali:latest`.
2. **Конфиг backendّа.** В config.yaml Тройки прописать docker-окружение
   `kali`: image `troika-kali:latest`, ресурсы (CPU/RAM лимиты), network,
   forward_env пустой (секреты не пробрасываем).
3. **Деплой tool'а.** Выкатить ветку с `workspace_tool.py` (docker cp патчей
   ПОСЛЕ recreate — recreate стирает /opt/hermes, это известная ловушка).
4. **Регистрация.** Убедиться, что tool попал в toolsets.py + troika-voice +
   skill voice-task-routing. Рестарт gateway `/command/s6-svc -r`.
5. **Проверка.** Голосом: «перейди в кали» → «покажи версию nmap» →
   «вернись обратно». Проверить, что в основном окружении инструментов Kali нет
   (изоляция работает), а в kali — есть.

## Что это даёт и чего НЕ даёт

**Даёт:** Тройка по команде уходит в изолированное Kali-окружение, гоняет там
весь арсенал, результаты в /work, потом возвращается. Секреты не утекают.
Контейнер можно снести и пересоздать за секунды. Аудит-лог фиксирует действия.

**НЕ даёт (сознательно):** сокрытие источника атаки/анонимизацию ради уклонения
от обнаружения, и автоматическую работу по произвольным чужим целям без фиксации
ответственности. Это вне рамок — инструмент пентестера, не инструмент взлома.

## Оценка работы

- Код (`workspace_tool.py` + session-scoped backend switch + аудит-гейт):
  средний объём, 1 заход. Главная сложность — переключение backend'а per-session
  (п.2).
- Сервер (образ + конфиг + деплой): полчаса, делаешь ты по инструкции.
- Риск для прода: низкий — новый tool аддитивен, не трогает существующие пути;
  backend Kali отдельный, основное окружение Тройки не меняется.
