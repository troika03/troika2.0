# Подключение месячного ресурса и оплаты Troika

Состояние на 14 октября 2026 года: месячный runtime и личный API включены
на production. Оплата и письма по просьбе владельца отложены. Secrets не
передавать в переписку, Git и отчёты. Результаты — в
[аудите](../audit/SUBSCRIPTION_RUNTIME_2026_10_13.md).

Через ключ Тройки бесплатная модель списывает полный prompt + completion,
включая cached input. Reasoning повторно не добавляется. Личный OpenRouter/OpenAI
не расходует токены подписки за вызовы модели; платный голос сервиса учитывается
отдельно. Права тарифа и task concurrency сохраняются. Ключ приходит только
в текущий HTTPS-запрос через X-Troika-Provider-Key/Provider/Provider-Model,
не включается в body, history, export или idempotency key и не сохраняется сервером.
Неверный ключ не разрешает fallback на корпоративные credentials.

Android хранит ключ в RAM, режим/модель — на устройстве. После перезапуска
нужен повторный ввод; без него запрос блокируется, а не становится платным
корпоративным вызовом. WPF защищает ключ DPAPI CurrentUser для данного аккаунта.
Личный API включается операторским `product_byok_enabled: true`; default false.

Рабочие коэффициенты: `deploy/production/resource-beta.yaml`. Для Free
`debit_mode: model_tokens`, для остальных моделей — расчёт по цене. Коэффициенты
используют сценарий 120 ₽/USD + 15%, а не выдают его за текущий курс или счёт.
Взята верхняя ставка доступных endpoint-вариантов на момент проверки.
[OpenRouter Free](https://openrouter.ai/openrouter/free),
[Qwen](https://openrouter.ai/qwen/qwen3-coder-next),
[GPT Mini](https://openrouter.ai/openai/gpt-5.4-mini),
[Gemini](https://openrouter.ai/google/gemini-3-flash-preview),
[Groq](https://console.groq.com/docs/speech-to-text).

Две прежние Pro beta-учётные записи получили по 10 млн до 14 ноября. Это
доверенная операторская выдача, не покупка. Free/Welcome фонд 13 333 333 вместе
с этой выдачей 20 млн укладывается в первоначальный сценарий 1 000 ₽.
Месячный ресурс/голос включены, `product_billing_enabled` и verification — false.
Следующие абзацы описывают подключение продажи, которое пока не выполняется.

## Конфигурация и безопасный порядок подключения

Обычные настройки расположены в `platforms.api_server.extra` файла
`config.yaml` активного серверного профиля. Секреты находятся в `.env` этого
профиля. Дефолты сохраняют новый ресурс, оплату и подтверждение почты выключенными.
Сначала испытать отдельный сервер и тестовые аккаунты; production баланс и
оплаченные права пользователей не менять автоматически.

```yaml
platforms:
  api_server:
    extra:
      product_resource_enabled: false
      product_resource_text_enabled: false
      product_resource_prices: {}
      product_resource_services: {}
      product_resource_task_tokens: 250000
      product_resource_approval_tokens: 100000
      product_resource_subsidy_tokens: 33333333
      product_billing_enabled: false
      product_billing_test: true
      product_billing_shop_id: ""
      product_billing_return_url: ""
      product_verification_enabled: false
      product_verification_smtp_host: ""
      product_verification_smtp_port: 465
      product_verification_smtp_ssl: true
      product_verification_smtp_username: ""
      product_verification_sender: ""
      product_verification_reviewed_users: []
```

Флаги `product_resource_enabled` и `product_resource_text_enabled` представляют
полный staged режим и прежний этап проверки текстового адаптера соответственно.
Для месячного режима достаточно первого; не включать его на production ради
одной лишь доступности кнопки оплаты. В этом режиме дневной счётчик запросов
уступает место месячному ресурсу, а технический rate limit остаётся.

Каталог `product_resource_prices` индексируется точным ID модели. Каждая запись
содержит `provider`, `version`, `input_rub`, `output_rub`, `cache_read_rub`,
`cache_write_rub`, `premium`, `default_output_tokens`, `maximum_output_tokens`.
Цены — полная стоимость в рублях за миллион реальных токенов с учётом закупки
и комиссий. Каталог должен охватить основную модель, auxiliary, compression
и все разрешённые workers. Не копировать иллюстративный валютный курс из
экономического сценария как фактическую цену.

Для подтверждённого vision-маршрута добавляется `vision_input_tokens`: проверенная
верхняя граница на одно изображение, до четырёх изображений за вызов. Без этой
границы мультимодальный вызов блокируется. Общие legacy vision/image-generation
tools остаются закрытыми в новом режиме до отдельного адаптера.

Каталог `product_resource_services` содержит ключи `groq:whisper-large-v3-turbo`, `fish:tts`,
`edge:tts`. Поля каждой записи: `version`, `unit`, `rub_per_unit`,
`minimum_units`, `maximum_units`. Groq использует `seconds`, оплачиваемый минимум
не меньше 10 секунд и верхнюю границу не больше 180 секунд. TTS использует
`characters`; граница должна соответствовать реальному ограничению маршрута.
Нулевая ставка Edge допустима только при подтверждённом отсутствии платы.
Локальная обработка не получает вымышленного облачного списания.

Коэффициенты фиксируются при первом использовании конкретного сервиса внутри
периода. Последующее изменение останавливает новые вызовы. Каталог ещё не
фиксируется целиком в момент покупки; до продажи нужны опубликованная версия
условий и управляемая процедура согласования изменений. Не удалять записи
с pending reserves и не считать timeout доказательством бесплатного вызова.

## ЮKassa

1. Подключить магазин в кабинете оператора. В серверном профиле задать
   `product_billing_shop_id`, согласованный HTTPS `product_billing_return_url`
   и секрет `YOOKASSA_SECRET_KEY`. Начать с отдельного тестового магазина и
   `product_billing_test: true`.
2. Настроить HTTPS-уведомления `payment.succeeded` и `refund.succeeded` на
   `/v1/billing/webhook` адреса API. Уведомление только запускает сверку:
   сервер получает объект через авторизованный API ЮKassa и сверяет сумму,
   валюту RUB, магазин, идентификатор намерения и test-признак. Redirect из
   браузера и переданное клиентом «оплачено» не выдают ресурс.
3. На испытательном сервере включить полный ресурс и billing. Проверить
   `GET /v1/billing`, `POST /v1/billing/checkout`,
   `GET /v1/billing/{intent_id}`, повтор webhook и тайм-аут создания платежа.
   Тестовый успех записывается как `test_succeeded`, без реального grant.
   Обычные клиенты скрывают покупку в test-режиме; испытание API выполнять
   отдельным тестовым аккаунтом.
4. Проверить полный возврат, очередь продления/смены тарифа, конец периода,
   logout во время платежа и два устройства. Ручное продление использует новый
   явный платёж; карточка не сохраняется, автоматическое списание не запрашивается.
5. Перед live-режимом закрыть настройку чеков и требований магазина, политику
   возвратов, контакт поддержки, обработку partial refunds и удаление аккаунта
   с pending payment. В этой версии нет API создания возврата: оператор делает
   возврат в кабинете, сервер сверяет событие полного возврата. Частичный
   возврат требует разбора и не меняет доступ молча.

Первый платный период начинается после подтверждённой оплаты; месячный Free
не суммируется с ним. Продление и смена уже оплаченного тарифа становятся
следующим периодом. Немедленный upgrade с prorating пока не реализован.
Докупка имеет отдельный срок 90 дней. Возврат отзывает неиспользованную часть
соответствующего grant; ранее отправленные резервы остаются до сверки.

Android и Windows сохраняют ключ незавершённой покупки между перезапусками.
Неизвестный результат повторяется с тем же ключом. Сервер отказывается
заново создавать неразрешённый intent старше 23 часов: нужна сверка оператора,
а не новый платёж автоматически.

Первичные источники: [уведомления](https://yookassa.ru/developers/using-api/webhooks),
[тестирование](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing),
[возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds).

## Подтверждение почты и Welcome

Настроить SMTP-сервис, отправителя, доменную доставку и TLS. Значение
`product_verification_smtp_ssl: true` означает implicit TLS; `false` использует
STARTTLS, а не открытый транспорт. Пароль `TROIKA_SMTP_PASSWORD` и независимый
секрет HMAC `TROIKA_EMAIL_VERIFICATION_SECRET` длиной не меньше 32 символов
хранить только в серверном `.env`. При использовании SMTP-логина пароль
передаётся этому серверу; не включать debug-логирование писем и кодов.

На испытательном сервере включить `product_verification_enabled`.
`POST /v1/account/verification/request` отправляет код только на почту владельца;
`confirm` принимает `id` и `code`, `welcome` проверяет право на бонус.
Код действует 10 минут, допускает пять попыток. Между письмами минимум
60 секунд, не больше пяти писем в день. БД хранит HMAC, а не код; сбой
отправки не активирует подтверждение. Смена почты требует нового подтверждения.

Подтверждённая почта сама по себе не защищает от регистрации множества
аккаунтов. Welcome разрешён для списка проверенных beta-аккаунтов
`product_verification_reviewed_users` либо после реальной сверенной оплаты.
Пользователь не может передать себе право на бонус. Тестовый платёж такого
права не создаёт. Это ограниченный beta-порядок, а не готовая публичная
anti-abuse система.

Общий первоначальный предел — 33 333 333 расчётных токена в календарный месяц;
после существующей beta-выдачи Free/Welcome получает 13 333 333,
то есть не больше 1 000 ₽ по согласованному коэффициенту. Он ограничивает
новые Free/Welcome grants, сохраняя уже выданное. Когда фонд исчерпан,
Free-период может иметь нулевое финансирование, но ранее купленная докупка
доступна. Такой период не получает пополнение автоматически при изменении
фонда. Публичное обещание Free требует доступного финансирования и условий
ограниченного приёма. Автоматическая связь фонда с 10% оплаченной выручки
ещё не реализована. Агрегат выдачи сохраняется после удаления аккаунта;
политику хранения и защиту от повторных регистраций нужно завершить до запуска.

## Проверка перед переключением production

До продаж обязателен свежий E2E установленного Android/Windows с реальными маршрутами:
полный input, cache, reasoning, auxiliary, voice, разрешённый vision, успешная
предметная квота на весь Run, два устройства, исчерпание, approval, Stop,
logout/revoke, неизвестный bill, дубликат платежа и возврат. Сверить реальные
счета провайдеров с численными receipts, не сохранять prompts и raw media.
Веб-кабинет также требует E2E и сохранения ключа незавершённого checkout
между перезагрузками; готовность Android/Windows не доказывает этот путь.

До открытия продаж также нужны сверка зависших резервов, оплата компанией
технических сбоев, финальная миграция существующих оплаченных прав, контроль
всех платных маршрутов, каталог цен и production backup/deletion. Сейчас
автоматическое возмещение ошибок Troika и операторский интерфейс сверки
не реализованы. Unit-тест и сборка не закрывают эти критерии.

После проверки сохранить версию клиента/сервера, результаты и процедуру
отката. Переключать флаги можно только с сохранением текущих данных и
обязательств; не выдавать платный период из старого дневного лимита.


## Управление текущим развёртыванием

Использовать прежний Compose и сохранённые оператором отдельные image tags:

```bash
cd /srv/troika/current/deploy/production
docker compose --env-file resource-images.env -f compose.yaml up -d --no-build
```

STT имеет отдельный `TROIKA_STT_IMAGE_TAG` и тот же read-only config. Перед
обоими обновлениями сделаны защищённые серверные SQLite backups и копии config.
Откат не восстанавливает старый DB snapshot поверх новых пользовательских
данных. Конфигурация и образы можно откатить отдельно; pricing pins изменённого
правила Free также требуют согласованного обратного перехода. Старые receipts
и остатки не переписываются. Цена фиксируется для каждого сервиса периода.

Текущий API image включает дополнительный слой persona: подробные инструкции
разработки загружаются через capability discovery. Две gateway schemas и
отсутствие автоматического списка навыков проверены на сервере. Локальное
сокращение блока 3 303 до 2 674 токенов не означает такой же процент всего
production bill. План: [входной контекст](INPUT_TOKEN_PLAN.md).
