# Тройка: план перехода от прототипа к продукту

**Статус:** рабочий план

**Дата основания:** 2026-09-09

**Главное решение:** Тройка становится подписочным персональным AI-ассистентом. На первом релизе она продаёт надёжное ежедневное взаимодействие — текст, голос, задачи и приватный контекст — а не количество инструментов. Опасные и экспериментальные возможности остаются выключенными по умолчанию.

Подробный порядок восстановления старых возможностей, включая безопасное
зрение через экран и камеру телефона: [docs/TROIKA_CAPABILITY_RESTORATION_PLAN.md](docs/TROIKA_CAPABILITY_RESTORATION_PLAN.md).

## 1. Цель продукта

### Продуктовое обещание

> Тройка — русскоязычный персональный AI-ассистент, с которым можно говорить или писать: он понимает контекст, помогает с задачами и бережно хранит только данные владельца.

Первый платный продукт не должен обещать «автономно управляет всей жизнью». Он обязан предсказуемо выполнять несколько повторяемых задач быстрее, чем обычный чат:

1. Голосовой и текстовый диалог в одном контексте.
2. Создание и напоминание о задачах.
3. Поиск, краткое исследование и создание документов.
4. Личная память, которую пользователь видит, исправляет и удаляет.

### Целевая аудитория первой беты

Русскоязычные индивидуальные пользователи: основатели, специалисты и занятые люди, которые регулярно работают с задачами, заметками и документами. Не начинать с компаний, семейных аккаунтов, детей, критической медицины, финансовых рекомендаций или автономного управления компьютером.

### Принцип продукта

**Сначала доверие и надёжность, затем автономность.** Если функция может отправить сообщение, потратить деньги, открыть приватный файл, изменить данные или управлять компьютером — она должна быть ограничена, объяснена и подтверждена человеком.

## 2. Текущее состояние

### Уже есть и стоит сохранить

| Область | Состояние | Решение |
|---|---|---|
| Python agent + gateway | Богатое ядро, OpenAI-совместимый API, tools, сессии | Сохранить как внутренний execution layer, постепенно выделять продуктовые сервисы. |
| Android/Flutter клиент | Чат, голос, стриминг, разрешения, файлы | Оставить главным клиентом MVP, привести к безопасному onboarding. |
| Web dashboard | Собирается, есть административная и чат-поверхность | Оставить как операторскую/веб-поверхность, не делать единственным каналом. |
| Голос, STT/TTS | Есть несколько путей и провайдеров | Оставить один поддерживаемый путь в MVP, все остальные — feature flags. |
| Документы и исследования | Ценная основа для paywall | Оставить, но ограничить квотами и безопасными очередями. |
| Docker/CI/uv lock | Есть база для воспроизводимой поставки | Довести до staging/prod и обязательных проверок. |

### Нельзя выпускать как есть

1. Общий ключ, вшитый в APK, и HTTP-подключение к публичному IP.
2. Персональные константы `phone-misha`, один общий SOUL/контекст и общая память.
3. PC GUI, буфер обмена, запуск приложений и screen capture в default toolset.
4. Хранение точного GPS, Wi-Fi/Bluetooth fingerprint без понятного согласия, изоляции и срока хранения.
5. Незакоммиченные функции и зависимости, которых нет в `pyproject.toml`/`uv.lock`.
6. Пустые smoke-тесты вместо проверки пользовательских сценариев.
7. Режимы Kali, self-improve, произвольное выполнение кода и автопилот для платного MVP.

## 3. Границы первой версии

### Включить в public MVP

- Авторизация, профиль, устройства и управление сессиями.
- Текстовый чат, потоковый ответ, загрузка документов.
- Push-to-talk; wake word только после отдельного испытания качества и расхода батареи.
- Задачи/напоминания, заметки, история диалогов.
- Личные проекты: идеи, решения, задачи, сроки и полезные follow-up сообщения.
- Видимая память: просмотр, правка, удаление, очистка аккаунта.
- Документ/исследование как асинхронная задача со статусом.
- Тарифы, квоты, прозрачное сообщение об остатке лимита.

### Скрыть за feature flag / закрытой бетой

- Постоянный background listening и wake word.
- Геолокация и контекст Bluetooth/Wi-Fi.
- PC companion.
- Внешние мессенджеры, Telegram-автоматизация, отправка сообщений.
- Генерация медиа, тяжёлые coder-задачи, браузерная автоматизация.
- Одиночный снимок экрана: реализован с MediaProjection, одноразовой
  user/device session, Stop и лимитом кадра. Physical E2E безопасного экрана и
  opt-in vision provider, sensitive-screen fixture и threat-model review
  пройдены; функция остаётся выключенной по умолчанию и включается отдельно
  только для закрытой beta.

### Полностью выключить на старте

- Kali/security workspace.
- Самоизменение кода (`self_improve`) и автоматическое применение изменений.
- Неограниченный terminal/code execution.
- Любые действия от имени пользователя без конкретного подтверждения.

## 4. Целевая архитектура

```text
Android / Web / будущий Desktop Companion
                 |
          HTTPS + OIDC tokens
                 |
API edge: auth, rate limits, idempotency, audit
                 |
      Product API / application services
       |          |             |
 users/devices  billing       conversations/jobs
                 |
           Agent gateway
                 |
        provider router + tools
                 |
 Postgres / object storage / encrypted secrets / queue
```

### Чёткое разделение ответственности

| Компонент | Ответственность |
|---|---|
| Client | UI, безопасное хранение device token, явное согласие, отображение статуса и подтверждений. Никаких API-ключей моделей. |
| API edge | Проверка access token, `user_id`, `device_id`, rate limit, версия клиента, защита от повторных запросов. |
| Product API | Аккаунт, billing, entitlement, usage ledger, privacy requests, поддержка. |
| Agent gateway | Только выполнение разрешённой задачи в изолированном контексте пользователя. Не источник истины для подписки. |
| Tool workers | Асинхронные документы/исследования с timeout, бюджетом и журналом. |
| PC Companion | Отдельный локальный процесс, сопряжённый с одним устройством и требующий подтверждения для действия. |

### Обязательная модель данных

Каждая сущность получает `tenant_id`/`user_id` и проверяется на уровне запросов:

- `users`, `devices`, `sessions`, `refresh_tokens`;
- `subscriptions`, `entitlements`, `usage_ledger`, `invoices`;
- `conversations`, `messages`, `attachments`, `jobs`;
- `memories`, `saved_places`, `consents`, `audit_events`;
- `provider_credentials` — только зашифрованные и только если BYOK разрешён.

Для данных пользователя запрещены глобальные primary key вроде имени места. Пример: `saved_places` использует `PRIMARY KEY (user_id, name)`; все `SELECT`, `UPDATE`, `DELETE` фильтруют `user_id`.

## 5. Безопасность и приватность — P0

### Доступ и сеть

1. Убрать `hermes-2024`, публичный IP и любой дефолтный секрет из приложения, репозитория и образов.
2. В продакшне только HTTPS/WSS с доменом и HSTS; HTTP допускается лишь на localhost в development.
3. Регистрация устройства: одноразовый pairing code/QR → access token с коротким TTL + refresh token в Android Keystore.
4. Отзыв устройства, logout всех устройств, ротация refresh token, ограничение попыток входа.
5. Продовый API не принимает пользовательский `user_id` из заголовка: он извлекается из проверенного токена.

### Данные

1. Персональные память, геолокация, файлы и история строго разделены по пользователям.
2. Геолокация — opt-in permission c объяснением цели; по умолчанию выключена.
3. Координаты не отправляются в сторонние сервисы геокодинга без отдельного согласия. Если отправляются — фиксируются провайдер, цель и срок хранения.
4. Шифрование secrets at rest, резервных копий и транспорта; журнал доступа без содержимого сообщений и ключей.
5. Функции: экспорт данных, удаление аккаунта, настройка retention, очистка памяти и диалогов.

Сроки и честные границы удаления зафиксированы в
[docs/DATA_RETENTION_AND_DELETION_POLICY.md](docs/DATA_RETENTION_AND_DELETION_POLICY.md).
Owner-scoped личная память с просмотром/правкой/удалением, ZIP-экспорт и
удаление из текущих локальных основных хранилищ реализованы. Автоматическое
применение retention, production object storage, удаление из backup и проверка
восстановления ещё не реализованы.

### Инструменты и действия

1. Использовать capability-based toolsets: базовые безопасные tools, отдельно документы, отдельно integrations, отдельно PC.
2. `pc_*` исключить из `_HERMES_CORE_TOOLS` для облачного агента.
3. Каждое PC-действие требует локального explicit approval; `clipboard_get`, screen capture и ввод текста — особенно.
4. Любая отправка во внешний сервис показывает preview, получателя и последствия.
5. Добавить неизменяемый audit trail: пользователь, устройство, tool, параметры в редактированном виде, решение approval, результат.

## 6. Надёжность и качество — P0

### Воспроизводимая среда

- Python 3.11+ устанавливается единым `uv sync --extra ...` сценарием; Windows и Linux имеют проверенные команды.
- `scripts/run_tests.sh` получает Windows-эквивалент или становится кроссплатформенным Python runner.
- Все зависимости новых функций добавляются в `pyproject.toml`, имеют верхние границы по правилам репозитория, затем обновляется `uv.lock`.
- Android получает фиксированную версию Flutter в CI; TUI/web — lockfile и `npm ci`.

### Обязательные тесты

| Уровень | Минимум перед запуском |
|---|---|
| Unit | Auth, tenant isolation, quotas, usage ledger, TTS tags, location parser, tool approval. |
| API | Register/login/refresh/revoke, chat, SSE, files, billing webhooks, idempotency. |
| Security | No secret in APK, no tenant cross-read, denial of forbidden tool calls, rate limits. |
| Android | Login, onboarding, text chat, voice fallback, offline/error UX, token storage. |
| E2E | Новый пользователь → pairing → trial → чат → лимит → upgrade/cancel → delete data. |
| Load | Одновременные streaming sessions, job queue, provider failure, database restart. |

### Наблюдаемость

- Error tracking с release/version/device metadata.
- Метрики: uptime, p50/p95 latency, provider errors, STT/TTS success, job duration, token cost, approval rate.
- Алерты: расходы за час/день, всплеск 401/5xx, очередь jobs, падение gateway, рост отказов платежей.
- Health checks должны проверять реальные зависимости, но не раскрывать секреты.

## 7. Платежи и экономика

### Модель тарифа

Не обещать безлимитный agentic AI. Подписка даёт лимит использования, а не доступ к неограниченному расходу владельца.

| Тариф | Состав |
|---|---|
| Trial | Небольшой объём текстовых запросов и голоса; без опасных tools. |
| Personal | Базовый пакет сообщений, голосовых минут, память, задачи, документы. |
| Pro | Увеличенные лимиты, проекты, больше async jobs, закрытая бета PC companion. |
| BYOK add-on | Пользовательский ключ провайдера, хранимый зашифрованно; продукт всё равно лимитирует jobs и инструменты. |

### Финансовые правила

1. У каждой операции есть `estimated_cost`, `actual_cost`, `user_id`, тариф и причина списания.
2. Daily/monthly user caps и global platform cap. При превышении — безопасная остановка, не скрытый минус.
3. Дорогие coder/research jobs показывают оценку и требуют подтверждения.
4. Billing webhook идемпотентен, подписка имеет понятные статусы: trial, active, grace, past_due, cancelled, blocked.
5. До подключения платежей подготовить условия использования, политику приватности, возвраты, контакты поддержки и требования юрисдикции с профильным юристом.

## 8. Порядок реализации

### Фаза A — заморозка риска (1–2 недели)

- [ ] Не добавлять крупные функции до закрытия P0.
- [ ] Зафиксировать новую рабочую копию и закоммитить текущие нужные наработки отдельными тематическими коммитами.
- [ ] Убрать из public default PC/Kali/self-improve и персональные константы.
- [ ] Восстановить Python env, web/TUI/Flutter checks, сделать baseline CI зелёным.
- [ ] Создать staging окружение, отдельное от личного gateway.

**Выход:** проект собирается и тестируется воспроизводимо, без публичных секретов и персональных defaults.

### Фаза B — мультипользовательское ядро (2–4 недели)

- [ ] Ввести user/device/session model и миграции базы.
- [ ] API auth, pairing QR, token rotation/revocation.
- [x] Перенести memory/files/location на user-scoped storage.
- [ ] Добавить quota/usage ledger и server-side limits.
- [ ] Реализовать privacy controls и audit events.
- [x] Добавить подтверждаемое удаление локального product-аккаунта: отзыв всех
      device tokens, остановка run/phone channels и очистка SQLite, SessionDB,
      transcripts, artifacts, location context и vision metadata без затрагивания
      другого пользователя.
- [x] Добавить self-service ZIP-экспорт всех переносимых данных и artifact bytes
      текущего владельца; тест с двумя пользователями доказывает изоляцию.
- [x] Добавить owner-scoped память с API и Android CRUD, безопасным prompt
      context, экспортом и cross-tenant тестами.
- [x] Определить retention-периоды и политику будущего удаления из backup/object
      storage без утверждения о ещё не реализованной очистке резервных копий.
- [ ] Реализовать и проверить автоматический retention worker, production
      object-storage purge, deletion ledger и restore scrubber.

**Выход:** два пользователя не могут увидеть, использовать или удалить данные друг друга; это подтверждается автоматическими тестами.

### Фаза C — надёжный MVP (2–3 недели)

- [ ] Stabilize Android onboarding, chat/SSE, error states, reconnect.
- [ ] Выбрать один основной STT и TTS путь, добавить fallback и метрики.
- [ ] Включить задачи, напоминания, документы и безопасный research queue.
- [x] Добавить активный личный проект и естественные команды «запомни»,
      «добавь задачу», «напомни»; внешние действия выполнять только после
      отдельного подтверждения.
- [x] Ограничить проактивность событиями по существу: срок, блокировка,
      ожидаемое решение, обзор прогресса или явно созданное напоминание.
- [ ] Настроить feature flags и админскую конфигурацию без redeploy.
- [ ] Добавить support flow и экспорт диагностических логов без секретов.

**Выход:** новый пользователь успешно начинает и завершает пять главных сценариев без ручной настройки сервера.

### Фаза D — закрытая бета (3–4 недели)

- [ ] Invite-only: 20–50 пользователей.
- [ ] Еженедельный разбор ошибок, расходов, retention и интервью.
- [ ] Нагрузочные тесты и disaster recovery rehearsal.
- [ ] Подключить billing в test mode, затем ограниченный production rollout.
- [ ] PC companion только группе добровольцев с локальными approvals.

**Выход:** метрики и отзывы доказывают, что core loop используют повторно и он окупается.

### Фаза E — публичный запуск

- [ ] Сайт, pricing, legal pages, FAQ, support SLA и статус-страница.
- [ ] Мониторинг и on-call процесс.
- [ ] Ограниченный rollout, kill switch для tools/провайдеров/релизов.
- [ ] Публичная подписка только после прохождения launch gates ниже.

## 9. Launch gates

Платные продажи не открываются, пока не выполнено всё:

- [ ] Нет общего ключа, HTTP публичного API и персональных идентификаторов в клиентах.
- [ ] Есть проверенная изоляция пользователей и удаление данных.
- [ ] CI выполняет unit/API/security/Android checks.
- [ ] Успешный staging deploy и rollback проверены.
- [ ] Есть лимиты расходов и usage ledger.
- [ ] Есть privacy policy, terms, платежный процесс и поддержка.
- [ ] Dashboard, gateway и mobile имеют error monitoring и alerts.
- [ ] Основные пользовательские сценарии проверены на реальных beta users.
- [ ] PC/Kali/self-improve не могут случайно включиться для обычного пользователя.

## 10. Метрики, по которым принимать решения

### Надёжность

- API availability, p95 latency, failed stream rate, STT/TTS completion rate.
- Crash-free Android sessions и время восстановления gateway.

### Пользовательская ценность

- Activation: пользователь завершил первый полезный сценарий в первые 10 минут.
- Week-1/Week-4 retention.
- Количество успешно завершённых задач/документов, а не число вызовов LLM.
- Доля запросов, закончившихся ошибкой или ручным повтором.

### Экономика

- Cost per active user, gross margin по тарифу, расход на task.
- Abuse/fraud rate, доля пользователей в лимите, chargeback/refund rate.
- Conversion trial → paid и monthly churn.

## 11. Первые задачи в новом workspace

1. Создать ветку `codex/product-foundation`.
2. Инвентаризировать все personal/default constants, public endpoints и секреты; закрыть их feature flags.
3. Сначала спроектировать миграцию user-scoped storage и API auth, затем вносить код.
4. Вернуть воспроизводимое окружение и зелёный minimal CI.
5. Написать tests, которые воспроизводят текущие критические дефекты: cross-tenant location, hardcoded key, PC tools in default toolset, missing dependencies.

Порядок важен: не подключать real billing до auth, tenant isolation и usage ledger.
